# Cluster: self-host

## Summary

`main` built out a three-layer upgrade story that did not exist at `BASE`: a machine-readable release-safety
signal (`upgrade-safety.mdx`, "whether"), a full execution runbook (`upgrade-runbook.mdx`, "how"), and a
rewritten `update-lightdash.mdx` that keeps versioning policy plus new security-advisory monitoring and a CLI
version-match reminder. Separately it rewrote the enterprise license-keys page into a real reference (feature
flag table + SSO provider table + roadmap egress), added the `pgvector` requirement, `RESULTS_S3_*` separate
query-results storage, and a new organization-roadmap page.

The refactor meanwhile merged `update-lightdash` + `upgrading-lightdash-versioning` + the checklist's upgrade
content into one page, `self-host/upgrading.mdx`. That page and main's runbook now cover the same mechanics
(helm sequence, migration job, `knex_migrations_lock`, rollback) and **contradict each other**: `upgrading.mdx`
still tells operators to release the migration lock by hand and to gate rollback on "release notes say
migrations are backwards-compatible", both of which main supersedes for Lightdash `1.123.0`+. Resolving that
split — `upgrading` keeps policy/cadence/advisories, the runbook owns execution and recovery — is the core of
this catch-up. Everything else ports cleanly once links are re-pointed through the rename map.

## Flags

- **Contradictory migration-lock guidance (row 7).** `self-host/upgrading.mdx:63` and
  `configure-lightdash-to-use-an-external-database.mdx:70` both say to release `knex_migrations_lock` by hand.
  Main documents that as actively harmful on Lightdash `1.123.0`+ — it can free a lock a live migration holds.
  This is the one place the branch is currently *wrong*, not merely stale; fix it wherever the rest lands.
- **Rollback rule superseded.** `upgrading.mdx:67` gates rollback on "the release notes say the migrations are
  backwards-compatible". Main's model is different and more specific: rollback is forward-safe because the
  image classifies the ledger itself on `1.123.0`+, with `ALLOW_MISSING_MIGRATIONS=true` needed only below that
  fence. Reconcile to main's version.
- **Wrong env var on `enterprise-on-prem.mdx:36`:** `AI_AGENTS_ENABLED`. Both the env-var reference
  (`environment-variables.mdx:338`) and main's rewritten license page say `AI_COPILOT_ENABLED`. Row 10 removes
  the table anyway, but worth a `#verify` if the table survives in any form.
- **Three upgrade pages, or one?** I recommend three flat siblings under `self-host/` (rows 1–3): the
  decide/execute split is main's own design and the content volume supports it. The alternative — nest
  `upgrade-safety` and `upgrade-runbook` under a `self-host/upgrading/` group with `upgrading` as root, like
  `nats-workers` — is tidier in the sidebar but changes `/self-host/upgrading`'s URL and forces re-pointing the
  two redirects that already target it. Winnie's call; flat is my recommendation.
- **`upgrade-runbook.mdx` is 3,351 words**, past the principle-10 review trigger. References often pass, and
  this one is genuinely four procedures plus a command reference. If it should split, the natural seam is
  §§ Recovery + Rolling back into a `self-host/migration-recovery` page — but I'd ship it whole and let the
  next audit decide.
- **`Customize deployment` nav group is already 17 children**; row 11 makes it 18, well past the ~12 sectional
  review trigger (principle 12). Pre-existing on the branch, not introduced by `main` — noting it so it doesn't
  read as new debt from this merge.
- **Snippet candidate, not blocking:** the `🛠 This page is for engineering teams self-hosting…` `<Note>` is
  copy-pasted across 15 branch pages and both new pages add a 16th and 17th. A `snippets/self-host/cloud-note.mdx`
  would be a clean principle-5 win, but it's corpus-wide cleanup rather than catch-up work.
