Every query Lightdash runs uses a warehouse account: one shared by everyone, each person's own, or a mix of both. Your choice sets whether Lightdash or your warehouse controls who sees which data, and how much setup people do before they see a chart.

## Choose a setup

Start with one shared connection. Go through these questions in order and use the first setup that fits:

1. **Do data permissions need to live in the warehouse, as table access, row access, or audit by person?** If Lightdash roles and user attributes are enough, use [one shared connection](#one-shared-connection).
2. **Do the groups that need different data lack warehouse accounts of their own?** Use [a project per audience](#a-project-per-audience).
3. **Do most people view dashboards, or explore and write SQL?** If most view dashboards and your warehouse is Trino, Databricks, or BigQuery, use [optional personal credentials](#optional-personal-credentials).
4. **Does your warehouse have a sign-in flow for personal credentials?** If it does, use [required personal credentials](#required-personal-credentials). If it doesn't, requiring them means issuing a warehouse login to every viewer, so compare that with [a project per audience](#a-project-per-audience).

## One shared connection

Everyone queries as one warehouse account, set on the [project connection](/integrations/connect-project#choose-how-to-connect-your-warehouse). Make it a dedicated read-only account, not a person's own sign-in.

Use it when Lightdash roles are enough to control what people can do, and everyone in the project may see what that account can read. Most teams should start here: people see dashboards as soon as they're invited, and scheduled deliveries, embedding, and service accounts work without extra setup.

The warehouse sees one user, so its permissions can't differ by person and its audit logs show only the shared account. Lightdash [roles](/workspace-admin/roles) control who can explore or open the [SQL runner](/explore/sql-runner), not which tables or rows the warehouse returns. Anyone with `manage:SqlRunner` can query everything the shared account can read. Developers and Admins have that permission by default. A [custom role](/workspace-admin/custom-roles) can leave it out, but it [can't remove a permission](/workspace-admin/custom-roles#how-additive-permissions-work) someone already has from their organization role.

To limit what people see without changing the warehouse, use [user attributes](/workspace-admin/user-attributes#using-user-attributes-in-lightdash). They filter rows and hide fields in everything built from the semantic layer, but they don't apply to [raw SQL](/agents/agent-access-to-restricted-data#keep-raw-sql-away-from-restricted-roles).

This works with every warehouse.

## Required personal credentials

Each person queries as themselves, so table access, row access, and audit stay in the warehouse. Turn on **Require users to provide their own credentials** in the project's warehouse connection settings, and everyone adds [personal warehouse credentials](/personal-settings/personal-warehouse-connections).

Use it when access rules already live in the warehouse, you need audit by person, or developers need raw SQL without seeing everything, and your warehouse has a sign-in flow.

Everyone has to add credentials before they see any data, including people who only view dashboards. With a sign-in flow, that's one sign-in. Without one, each viewer needs a warehouse login issued for them.

Some features work differently:

- [Service accounts](/workspace-admin/service-accounts#warehouse-credentials) can't run queries.
- [Embedding](/embed/set-up-embedding) isn't available, because embedded viewers can't provide credentials.
- [Scheduled deliveries](/explore/create-scheduled-deliveries#reassigning-scheduled-delivery-owners) run with their owner's credentials, and fail if the owner's are missing or expired.
- [Pre-aggregates](/semantic-layer/pre-aggregates#not-supported) aren't compatible with personal credentials.
- [Cached results](/semantic-layer/caching#user-level-caching) are stored per person, so one person's query doesn't speed up anyone else's.

The setting is on the connection form for BigQuery, Snowflake, Databricks, Redshift, PostgreSQL, Trino, and ClickHouse. The Athena and DuckDB forms don't have it.

Four warehouses have a sign-in flow for [personal credentials](/personal-settings/personal-warehouse-connections#supported-authentication-methods):

- **Snowflake:** **Sign in with Snowflake**, once you [add a security integration](/integrations/connect-project#sign-in-with-snowflake).
- **Databricks:** **Sign in with Databricks**, on instances with Enterprise enabled and an [OAuth application](/integrations/connect-project#sign-in-with-databricks).
- **BigQuery:** **Sign in with Google**.
- **Redshift:** **Sign in with AWS**, through [IAM Identity Center](/integrations/connect-project#redshift). Everyone gets the one permission set fixed on the connection, so it replaces passwords but doesn't give people different access.

Trino, PostgreSQL, and ClickHouse take a username and password.

## Optional personal credentials

A shared connection serves most people, and anyone who adds [personal credentials](/personal-settings/personal-warehouse-connections#when-are-personal-warehouse-credentials-used) queries as themselves.

Use it when most people view dashboards and a small group, usually developers or analysts, needs their own warehouse permissions. On warehouses that support it, choose this over required credentials: viewers need no setup, and service accounts and embedding keep using the shared connection.

People add personal credentials themselves, so anyone who hasn't still queries as the shared account, including SQL runner users. Limit the shared account to data every project member may see. Two people can also get different results from the same dashboard, or one can get a warehouse permission error, depending on whose credentials run the query.

Trino and Databricks use personal credentials whenever **Require users to provide their own credentials** is off. BigQuery uses them when you also turn on **Use personal credentials when available** in the connection's advanced settings. Other warehouses use personal credentials only when the project requires them.

## A project per audience

Each audience gets its own [project](/workspace-admin/manage-projects), with a warehouse connection limited to the data that audience may see.

Use it when groups must see different tables or datasets and don't have warehouse accounts of their own, such as separate business units or client teams.

Each project has its own spaces, charts, and dashboards, so content several audiences share is duplicated in each project, and every model change has to be deployed to each one. [Promoting content](/explore/promote-content) copies individual charts and dashboards to another project, but keeping the copies in sync is up to you.

A project separates only people whose organization role doesn't already give them access to it. [Organization roles](/workspace-admin/roles#organization-vs-project-roles) above **Member** apply to every project, so keep each audience at **Member** and give them one project role.

This works with every warehouse, and each project can use any of the setups above.

## Add credentials for someone else

If someone can't add their own credentials, an organization admin can [impersonate them](/support/support-access#impersonation-by-your-admins) and add credentials under **Settings** → **My warehouse connections**. Impersonation is off until it's enabled for your organization. Use a password, key, or token issued for that person. A **Sign in with** button saves whichever warehouse account your browser is signed in to, so it would store your identity under their name.

## Service accounts

[Service accounts](/workspace-admin/service-accounts) are for the API and CLI. They have no personal warehouse credentials, so their queries run on the shared connection, and a project that requires user credentials refuses them. If a script or pipeline queries the project through a service account, use one shared connection or optional personal credentials.
