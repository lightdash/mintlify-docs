For organization-wide reporting with editable charts and built-in dashboards, use the [usage analytics project](/workspace-admin/usage-analytics-project). It includes people, content, apps, AI and query activity.

This page covers two project-level ways of understanding user activity:

1. [**Usage Analytics dashboards**](#usage-analytics-dashboards) - these are dashboards created by Lightdash which give you an overview of your project's content and user activity.
2. [**Query tags**](#query-tags) - this is metadata which is added to your data warehouse queries and gives you information about who is querying data and what they are querying.

## Usage analytics dashboards

Each project has usage analytics dashboards created by Lightdash giving you an overview of your project's content and user activity.

To see your usage analytics dashboards for a project, just click on the `settings` icon, `project settings`, then `usage analytics`.

<Frame>
  ![The usage analytics entry in the project settings menu](/images/workspace-admin/usage-analytics/access-usage-analytics-84a955690c23e22d4a5594e76f134737.jpg)
</Frame>

Or you can also use our [search bar](/explore/search) to get direct access to the different analytics dashboards by typing the name of the dashboard (eg: User activity)

### User Activity dashboard

This dashboard gives you an overview of the users in your project and the activity of your users.

Opening it needs the **View Analytics** permission (`view:Analytics`) on the project. Among the built-in roles only Admins have it. To let other people open the dashboard, add `view:Analytics` to a [custom role](/workspace-admin/custom-roles) and assign it on the project.

<Frame>
  ![The User Activity dashboard with tiles counting users by role alongside charts of queries run over time](/images/workspace-admin/usage-analytics/user-activity-dashboard-e95a42bb99c5ed04f3434b1cbf9e5f4b.jpg)
</Frame>

Every tile counts the same roster of users: anyone with direct membership in the project, anyone with project access through a group, and anyone with an organization role above `Member` (or a custom organization role) — those roles get access to every project in the organization automatically, so they count here even if they never open this particular project.

Here's an overview of the fields used in the dashboard:

- **Number of users**: the total number of users that have access to the project.
- **Number of viewers**: the number of users with the `viewer` role that have access to the project.
- **Number of editors**: the number of users with the `editor` role that have access to the project.
- **Number of admins**: the number of users with the `admin` role that have access to the project.
- **% of weekly querying users**: the % of users which have run at least one query in the project in the last 7 days (out of all users in your project). Queries include viewing existing charts and dashboards.
- **Number of weekly querying users**: the number of users which have run at least one query in the project in the last 7 days.
- **Weekly average number of queries per user**: the rolling 7 day average number of queries that each user is running in your project.
- **Users that have run the most queries in the last 7 days**: a list of the users that have run the most queries in your project in the last 7 days.
- **Users that have updated the most charts in the last 7 days**: a list of users that have updated (including created) the most charts in the project in the last 7 days.
- **Users that have not run a query in the last 90 days**: a list of users that have not run a query in the project in the last 90 days. This includes viewing charts and dashboards.

This list can include users who hold an organization role above `Member` but don't work in this project — those roles get access to every project, so they show up here as inactive rather than being excluded from the roster.

#### Extended usage analytics

Self-hosted instances can set the `EXTENDED_USAGE_ANALYTICS=true` environment variable to add two extra tables to the User Activity dashboard:

- **Dashboard views (top 20)**: ranks dashboards in the project by total view count.
- **Chart views (top 20)**: ranks charts in the project by total view count.

Views are counted the same way here as in the view counter shown next to charts and dashboards in Lightdash. A dashboard view is counted each time the dashboard is loaded, including refreshes. A chart view is counted each time the chart is loaded, including each time it loads as a tile on a dashboard, so a chart usually has more views than the dashboard it sits on. Views aren't deduplicated per user or per day; hover over the view counter to see the number of unique viewers.

View counts are per dashboard and per chart. They don't record which dashboard tab a chart was viewed on, or clicks and other interactions with individual tiles. Tiles on a dashboard tab load the first time a viewer opens that tab, so charts on tabs nobody opens don't gain views. For more detailed reporting, see the [usage analytics project](/workspace-admin/usage-analytics-project#build-your-own-analysis).

#### Export raw views

Click **Export CSV** on the User Activity dashboard to download the project's raw chart and dashboard views. Each row is one view, with the item's type, name, UUID and space, the viewer's name and UUID, and the time to the second. The export holds the most recent 100,000 views, newest first, and has no date range.

Chart tiles on [embedded](/embed/reference) dashboards add chart views with an empty user, because embed viewers aren't Lightdash users, and embedded dashboards don't add dashboard views. To see which embed viewer ran a query, use the `embed` and `external_id` [query tags](#query-tags).

To get the same data from the API, authenticate with a [personal access token](/personal-settings/create-personal-tokens) whose user has **View Analytics** on the project:

- `GET /api/v1/analytics/user-activity/{projectUuid}` returns the dashboard's tables as JSON.
- `POST /api/v1/analytics/user-activity/{projectUuid}/download` returns a URL for the CSV export. Fetch that URL with the same `Authorization` header.

## Query tags

Query tags are metadata which is added to your data warehouse queries and gives you information about each query executed.

The following query tags are sent:

| Query Tag | Detail |
| --- | --- |
| organization_uuid | Lightdash organization unique identifier. |
| project_uuid | Lightdash project unique identifier. |
| user_uuid | User unique identifier for the user that triggered the query. |
| embed | `true` when the query ran as the embed viewer, for example from an embedded dashboard or chart. Not set for AI agent embeds, whose queries run as the write actor and carry its `user_uuid`. See [User metadata](/embed/reference#user-metadata). |
| external_id | The `externalId` from the embed token's [user metadata](/embed/reference#user-metadata), or the id Lightdash generates when the token omits it. Set together with `embed`. |
| explore_name | Name of the explore the query was run against. |
| chart_uuid | Chart unique identifier. Only set when the query originates from a saved chart. |
| dashboard_uuid | Dashboard unique identifier. Only set when the query originates from a dashboard. |
| saved_sql_uuid | Saved SQL chart unique identifier. Only set when a scheduled job is running a saved SQL chart. |
| scheduler_uuid | Scheduler unique identifier. Only set when the query is triggered by a scheduled delivery, alert, or Google Sheets sync. |
| scheduler_name | Human-readable name of the scheduler. Only set when the query is triggered by a scheduler. |
| job_id | Scheduler job identifier for a single run of a scheduler. Only set when the query is triggered by a scheduler. |
| app_uuid | [Data app](/data-apps) unique identifier. Lightdash sets it automatically when the query originates from a running data app. The value is reported by the app itself in a request header and isn't verified by the server, so treat it as a best-effort attribution signal for usage reports. |
| query_context | Which context the query was executed in. See [Query contexts](#query-contexts) below for the full list of values. |
| agent | `true` when an AI agent ran the query. Set with [agent identity](/agents/agent-identity#find-agent-queries-in-the-warehouse). |
| agent_surface | Where the AI agent ran, for example `mcp` or `slack_agent`. Only set with [agent identity](/agents/agent-identity#find-agent-queries-in-the-warehouse). |
| agent_client | The client of the AI agent, for example an MCP OAuth client ID or a Slack app ID. Only set with [agent identity](/agents/agent-identity#find-agent-queries-in-the-warehouse). |
| agent_uuid | The UUID of the Lightdash AI agent that ran the query, for in-app chat and Slack agents. Not set for MCP queries. Only set with [agent identity](/agents/agent-identity#find-agent-queries-in-the-warehouse). |
| user_attribute_`<name>` | One tag per [user attribute](/workspace-admin/user-attributes) value assigned to the querying user. Applies to both regular users and embed viewers, and requires no configuration. |

Query tags name the explore but not the metrics or dimensions a query selected. To count how often each field is used, use the **Semantic usage** explore in the [usage analytics project](/workspace-admin/usage-analytics-project#build-your-own-analysis).

### User attribute tags

For every query, Lightdash emits an extra `user_attribute_<name>` tag for each user attribute value assigned to the user running the query. This makes it possible to attribute warehouse cost, audit access, or debug row-level-security by user attribute directly from your warehouse's query history.

- Tags are emitted alongside the standard query tags for both signed-in users and embed viewers (using the attributes passed on the embed token).
- Values are carried through async query execution end-to-end, so they appear on the actual warehouse job (for example, as labels on a BigQuery job).
- Keys and values are sanitized to match warehouse tag constraints — lower-cased, restricted to `a-z 0-9 _ -`, and truncated if too long. Invalid or oversized metadata is sanitized rather than blocking the query.
- No configuration is required — user attribute tags are emitted automatically wherever query tags are already supported.

For example, a user with the `region` attribute set to `emea` and `customer_tier` set to `enterprise` will produce these additional tags on every warehouse query they trigger:

```text
user_attribute_region=emea
user_attribute_customer_tier=enterprise
```

You can then filter your warehouse's query or job history by these tags (for example, `labels.user_attribute_region = "emea"` in BigQuery) to break down usage or cost by user attribute.

Query tags are stored differently in each data warehouse:

| Data Warehouse | Query Tag                                                                                                                                                  |
| :------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BigQuery       | Writes metadata as labels in your [job history](https://cloud.google.com/bigquery/docs/managing-jobs#view%5Fjob%5Fdetails%5F2).                            |
| Snowflake      | Writes JSON metadata in the comment column of your [query history](https://docs.snowflake.com/en/user-guide/ui-history#viewing-query-details-and-results). |
| ClickHouse     | Writes JSON metadata in the `log_comment` column of your [query log](https://clickhouse.com/docs/operations/system-tables/query_log) (`system.query_log`).                            |
| Trino          | Sends metadata as comma-separated `key=value` pairs in the [`X-Trino-Client-Tags`](https://trino.io/docs/current/develop/client-protocol.html#client-request-headers) HTTP header on each submitted query. |
| Redshift       | Appends JSON metadata as a SQL comment in each submitted SQL query.                                                                                        |
| Databricks     | Appends JSON metadata as a SQL comment in each submitted SQL query.                                                                                        |
| Postgres       | Appends JSON metadata as a SQL comment in each submitted SQL query.                                                                                        |
| Athena         | Appends JSON metadata as a SQL comment in each submitted SQL query.                                                                                        |

### Attribute BigQuery cost with job labels

On BigQuery, every query tag is a label on the job. BigQuery records the account that ran the job in `user_email`. That is the connection's service account, the person's own Google account when they query with [personal warehouse credentials](/personal-settings/personal-warehouse-connections), or the agent's own account with [agent identity](/agents/agent-identity), never the Lightdash user. To find who a job ran for, read the `user_uuid` label. To find which AI agent ran it, read `agent_uuid`.

BigQuery allows 64 labels on a job. When a query has more tags than that, Lightdash keeps `agent`, `agent_surface`, `agent_client`, `agent_uuid` and `user_uuid` first, then the other query tags, then the user attribute tags. The labels beyond 64 are dropped, so `user_uuid` and the agent labels always stay on the job.

Lightdash writes labels on the jobs it creates in the connection's execution project. Query `INFORMATION_SCHEMA.JOBS` in that project. This needs the `bigquery.jobs.listAll` permission, for example from the BigQuery Resource Viewer role. Replace `region-us` with the region of your datasets.

<CodeGroup>

```sql Cost by Lightdash user
SELECT
  (SELECT value FROM UNNEST(labels) WHERE key = 'user_uuid') AS lightdash_user_uuid,
  COUNT(*) AS jobs,
  SUM(total_bytes_billed) / POW(1024, 4) AS tib_billed,
  SUM(total_slot_ms) / 1000 / 3600 AS slot_hours
FROM `region-us`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND job_type = 'QUERY'
  AND EXISTS (SELECT 1 FROM UNNEST(labels) WHERE key = 'query_context')
GROUP BY lightdash_user_uuid
ORDER BY tib_billed DESC;
```

```sql Cost by AI agent and user
SELECT
  (SELECT value FROM UNNEST(labels) WHERE key = 'agent_uuid') AS agent_uuid,
  (SELECT value FROM UNNEST(labels) WHERE key = 'agent_surface') AS agent_surface,
  (SELECT value FROM UNNEST(labels) WHERE key = 'user_uuid') AS lightdash_user_uuid,
  COUNT(*) AS jobs,
  SUM(total_bytes_billed) / POW(1024, 4) AS tib_billed,
  SUM(total_slot_ms) / 1000 / 3600 AS slot_hours
FROM `region-us`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND job_type = 'QUERY'
  AND EXISTS (
    SELECT 1 FROM UNNEST(labels) AS label
    WHERE label.key = 'agent' AND label.value = 'true'
  )
GROUP BY agent_uuid, agent_surface, lightdash_user_uuid
ORDER BY tib_billed DESC;
```

</CodeGroup>

`total_bytes_billed` drives on-demand cost, and `total_slot_ms` drives cost with capacity pricing. Label values are lower case, and any character other than a letter, digit, `_` or `-` becomes `_`, so `exploreView` is stored as `exploreview` and `mcp.run_metric_query` as `mcp_run_metric_query`. To match a `user_uuid` or `agent_uuid` to a name, compare it with the user or agent UUID in Lightdash.
