The **Lightdash analytics** project brings your organization's usage data into Lightdash. Start with the built-in dashboards, explore the underlying metrics, or save your own charts. You do not need to connect a warehouse or maintain a dbt project for it.

This project is separate from the [project-level User Activity dashboard](/workspace-admin/usage-analytics#user-activity-dashboard). It covers captured activity across your organization, rather than one project's fixed report.

Use this page to [create the project](#create-your-analytics-project), [grant access](#grant-access), [update its content](#update-models-and-dashboards), [choose a dashboard](#built-in-dashboards), [build your own analysis](#build-your-own-analysis), or [import retained history](#historical-backfill).

## Create your analytics project

1. Sign in with organization administration permissions.
2. Open **Settings → Lightdash analytics**.
3. Click **Create**. Lightdash creates the project and installs its built-in models, charts and dashboards.
4. Open a dashboard from the settings page, or click **Explore** to browse the available tables.

Organization administrators have access automatically. Other users need an explicit [analytics permission](#grant-access), even if they have access to other projects.

Creating the project starts a background [historical backfill](#historical-backfill) of supported records still held in the Lightdash database. You can use the project while it runs. Events without a retained database equivalent still require [normal capture and processing](#data-freshness-and-history).

## Grant access

The **View managed analytics for the entire organization** permission (`view:SystemAnalytics`) lets selected users, groups and service accounts read the analytics project without organization administration access. It is separate from **View usage analytics** (`view:Analytics`), which controls the older project-level usage reports.

Organization Admin includes this permission. Built-in Project Admin and other non-admin system roles do not; duplicating a Project Admin role does not add it either.

<Warning>
  The analytics project contains organization-wide usage, including user and content names. Assigning this permission on the analytics project does not limit the data to other projects the recipient can access. Grant it only to people or agents trusted to see usage across your organization.
</Warning>

### Configure a custom role

An organization administrator can grant access using [custom roles](/workspace-admin/custom-roles), which require an Enterprise plan:

1. Create a **Project** custom role and select **View managed analytics for the entire organization**. Keep its **View project** (`view:Project`) dependency selected.
2. Assign the role to the selected users, group or service account on the **Lightdash analytics** project.
3. Keep the ordinary permissions required for their work. Viewer access allows reading shared saved content; Interactive Viewer access or equivalent custom permissions is needed to build Explore queries. The analytics permission does not replace content, space or query permissions.
4. Have the recipient select **Lightdash analytics** in the project selector and open a dashboard. To verify query access, open a chart's **Explore from here** action and run a query.

The permission can also be included in an **Organization** custom role. A project-level assignment makes the intended access explicit. Follow [custom-role assignment](/workspace-admin/custom-roles#assigning-custom-roles) for users and groups, or [project-scoped service accounts](/workspace-admin/service-accounts#project-scoped-service-accounts) for automation.

Creating, syncing, backfilling and deleting the managed project through analytics settings still require organization administration permissions. The read permission does not grant those operations or access to SQL Runner, which is unavailable for managed analytics projects.

### Downloads and scheduled deliveries

You can download query results as CSV or Excel and use either format for [scheduled deliveries](/explore/create-scheduled-deliveries), subject to the usual export and delivery permissions. Other query-result download formats are unavailable on the analytics project.

CSV and Excel downloads require export storage. On a self-hosted instance, configure [S3-compatible object storage](/self-host/customize-deployment/configure-lightdash-to-use-external-object-storage). Without it, downloads and CSV or Excel deliveries fail with `Managed analytics downloads require export storage to be configured`.

### Agents and MCP

An agent uses the permissions of the user or service account it authenticates with. Grant access to that identity; granting it only to the service account's creator is not enough. The usual project, content, Explore and [MCP permissions](/agents/lightdash-mcp) still apply.

Use the managed Explores for metric queries. Test with the agent's actual credentials, including any required connection or token permissions.

### Remove access

Permissions are additive. Remove every applicable analytics grant, including direct, group and organization-level grants, to revoke access. An organization administrator retains access through their admin role.

After the normal permission/session refresh, revocation blocks project discovery, new queries, query history and cached results. It does not retract data already downloaded by a recipient.

## Update models and dashboards

When **Sync content** is available in **Settings → Lightdash analytics**, click it to install the built-in content supplied by your instance's release. Sync updates the models and built-in charts and dashboards in the existing project. You do not need to delete or recreate the project.

Duplicate a built-in dashboard before customizing it. Sync replaces edits to built-in content; custom dashboards and separate copies are kept.

Sync updates content definitions. It does not collect events, run the nightly data refresh, or add data from before capture was enabled.

## Built-in dashboards

Each dashboard groups related questions into tabs. The collection available to you depends on your deployed release and the content installed in your analytics project.

| Dashboard | What to use it for |
| --- | --- |
| **Adoption** | Active people, dashboard audiences, app loads and Ask AI usage over time. |
| **People** | Activity by person, usage trends and the channels people use. |
| **Content** | Content audiences, verification, ownership, observed use and known dependencies. |
| **Apps** | App loads, people using apps, app creation and AI consumption. |
| **Agents & AI** | Agent requests, technical outcomes, feedback, retries and model consumption. |
| **Queries** | Query response times, failures, workload origins, caching and semantic field usage. |
| **Tools & operations** | MCP tool calls, clients, errors, latency and exports. |

Chart descriptions explain the measure and its limits. Open a chart's **Explore from here** action to inspect its fields and filters before adapting it.

## Build your own analysis

Choose the Explore that matches what you want to count. An event, an app load, a person and an AI model call are different measures.

| Explore | What it measures |
| --- | --- |
| **User activity** | Daily activity grouped by user and event, with totals for captured queries, downloads, app views, AI usage and tool calls. |
| **Content reach** | Captured dashboard and chart views, identified viewers and observed return visits. |
| **Content health** | Content inventory, including items with no observed activity, plus ownership, verification and known dependencies. |
| **Data app reach** | App loads and distinct identified viewers, with the surface where each load occurred. |
| **Data app events** | Captured app lifecycle and usage events. |
| **Agent requests** | Human prompts, request outcomes, retries, feedback and associated consumption. |
| **AI usage** | Individual AI model calls and reported token usage, grouped by feature, provider or model. |
| **Agent steps** | Individual steps within agent execution. One request can involve several steps. |
| **Agent request events** | The captured request lifecycle events underlying Agent requests. |
| **Query events** | Captured query outcomes, error messages (up to 1,000 characters), timing, context and cache use, plus supported retained query history. It does not include compiled SQL. |
| **Semantic usage** | Direct metric and dimension references captured from queries. |
| **Export events** | Captured result-download events and formats. |
| **Tool activity** | MCP calls by tool, client, source and actor, including known outcomes and latency. |
| **Historical activity** | Retained database records recovered by [historical backfill](#historical-backfill), with their own activity types and counting rules. |

### Who uses which dashboards and apps?

Start with **Adoption → People & content** for dashboard audiences and **Adoption → Data apps** for app usage.

For a custom dashboard-usage table, open **Content reach**. Select **User name**, **Content name**, **Event ts → Day** and **Qualifying views**, and filter **Content type** to `dashboard`. Add **Space name** to group views by the space each item was in when it was viewed.

For app usage, open **Data app reach**. Select **User name**, **App name**, **Event ts → Day**, **Total loads** and **Distinct viewers**. Use **View context** to distinguish standalone apps, dashboards, charts and builder previews. To follow the Adoption dashboard's app-usage scope, select `standalone`, `dashboard` and `chart`. App usage is recorded per app load; Lightdash doesn't capture which tabs or elements inside an app people use.

These are separate Explores. Put their charts on the same dashboard to review them together; there is no combined dashboard-and-app viewer table in this collection. **User activity** can compare event categories by person and date, but does not supply the same per-content detail.

### How is Ask AI usage changing?

Start with **Adoption → Ask AI**, including **Ask AI questions each day** and **People asking AI each week**.

To build the trend yourself, open **Agent requests**:

1. Filter **Surface** to `web_app` for Ask AI in the Lightdash web app.
2. Select **Requested at → Day** or **Week**.
3. Add **Total requests** and **Distinct requesters**.
4. Add **Agent name** or **User name** to compare agents or people.

Total requests includes captured follow-up prompts and requests that are pending or failed. Use request status to narrow the analysis. Other surfaces, such as Slack, are outside the `web_app` filter.

Use **AI usage** for model calls and token consumption. Its `ai.usage` event represents a model call, not a question: one question can make several calls, and other AI features also make calls. Filter by **Feature** when comparing consumption. Tokens are not monetary cost or a complete measure of spending in external assistants.

## Data freshness and history

Usage data is collected after capture is enabled for your organization. The scheduled refresh processes closed UTC days at **00:30 UTC** and updates the snapshots used for names and content inventory. Allow that job to finish before expecting the previous day's data; these dashboards are not real-time monitors.

Captured history depends on when each event stream started and how long its files are retained. [Historical backfill](#historical-backfill) can recover supported database records from before capture began. It cannot reconstruct activity that was never stored. Names and inventory metadata can reflect the latest snapshot rather than the value at the event's time.

Keep these distinctions in mind when reading a chart:

- **Views and loads are observed activity.** Dashboard/chart views count qualifying backend fetches; app loads include reloads. They do not prove a person read the content or that an app rendered successfully.
- **Distinct users are not additive.** A person can appear on several days or use several items. Recalculate the distinct count for the whole period instead of adding daily or per-item counts.
- **No observed use is not proof of safe deletion.** Check the capture window and content dependencies before removing an item.
- **Missing values are unknown.** Historical errors, timings or identities may not have been captured; a blank value is not necessarily zero.

## Historical backfill

Backfill imports supported history that is still stored in your organization's Lightdash database into the analytics project. It can recover records from before event capture was enabled; it is not a replay of every past action or an import from your warehouse's query logs.

The **Historical activity** section in **Settings → Lightdash analytics** is available on releases that support backfill. Creating a project starts the import automatically. For an existing project, an organization administrator can click **Backfill available history** there. Projects that have already been collecting events for weeks or months can use the same action until a backfill succeeds.

The import runs in the background. You can leave the page and continue using Analytics. Imported datasets become queryable as they are published; no additional compaction run or overnight wait is required for those rows. Refresh an open chart or dashboard to load imported results. Names may remain unavailable until the normal metadata refresh finishes.

The action is disabled while backfill is running and disappears after a successful import, including when there are no eligible records. If the import fails, use **Backfill available history** again. If the status check fails, use **Retry check** first. A retry keeps completed work and does not duplicate imported records. **Sync content** does not start a backfill.

### What is included

All retained dates are eligible, including eligible records from today before each source is read. How far back you can go depends on database retention and when that kind of record began to be stored.

| Data | Where to explore it | What is recovered |
| --- | --- | --- |
| Queries | **Query events** | Completed queries and execution errors, including errors with no recorded warehouse execution time. Errors carry their retained error message, truncated to 1,000 characters. Includes available user, project, context, content IDs, execution time and row count. Historical dates use query submission time. |
| AI model usage | **AI usage** | Retained model-call records from the AI usage ledger: outcomes, model/provider, feature and reported token counts. This requires ledger records; conversation text alone cannot recreate model calls or token usage. |
| Chart, dashboard and app activity | **Historical activity** | Retained chart view-or-execution, dashboard view and app view records; app creation/deletion and version records. A chart execution is not necessarily a page view. |
| Agent activity | **Historical activity** | Retained thread, prompt, response/latest-retry, sharing, compaction, interruption, steering, routing, tool, research and delivery facts. Available status, feedback and prompt token totals describe stored snapshots. |
| Tools, exports and artifacts | **Historical activity** | Recorded MCP calls and permission decisions; download requests and export jobs; evaluation, artifact/version and file-upload records. A download request does not prove a successful download. |

Query and AI records join their existing datasets. If the same identity already has a captured event, the captured event takes precedence, including when it arrives after backfill. Existing data does not make the whole day ineligible: missing records can still be imported without overlapping identities being counted twice.

**Historical activity** uses different counting rules from captured events. Filter by **Activity type** and treat its rows as retained facts, not a complete event timeline. They are not added to the native view, request, tool or export totals. Do not add prompt or research snapshot token totals to **AI usage** model-call totals; they can describe the same underlying consumption.

### What is not included

- Activity never stored in a supported database record, or database records that have been removed or expired. Backfill cannot guarantee a fixed number of months of history.
- Preview-project queries and unfinished queries.
- Compiled SQL, conversation or reasoning text, tool arguments/results, uploaded file contents, credentials or export destinations. Query error messages are backfilled with the query; error text from other activity sources is not.
- Reconstructed historical names, ownership, permissions, missing identities, timings or a full sequence of status changes. Unavailable values remain unknown.
- Rebuilt historical **People / User activity** summaries or a replay into every captured-event Explore. Use **Query events**, **AI usage** and **Historical activity** for the imported data.

Backfill recovers selected facts belonging to your organization. It does not export the entire Lightdash database, and it is not continuous synchronization of database records after the import.

## Troubleshooting

### I cannot see Lightdash analytics in Settings

Check that your organization has access enabled and that your account has organization administration permissions. On a self-hosted instance, also check the [deployment prerequisites](/self-host/enterprise-features/usage-analytics).

### I have project access but cannot open analytics

Check that your account has **View managed analytics for the entire organization**, plus the ordinary project and content permissions. **View usage analytics** alone does not grant access to this project. Ask an organization administrator to follow [Grant access](#grant-access).

Readers open the project through the project selector; they do not need access to the admin-only analytics settings page. If an agent is denied, check its authenticated identity and effective permissions rather than its creator's access.

### Project settings open Lightdash analytics instead

The analytics project's settings can't be edited. While **Lightdash analytics** is the selected project, **Settings** → **Project settings** and project settings pages such as connection settings take you to **Settings** → **Lightdash analytics**. Only **Project access**, for users who can manage the project, and **Recently deleted** stay available.

To change your own project's connection or run a compile, select that project in the project selector first.

### "No analytics data is available yet"

This error appears until captured events for your organization have been through the [daily processing](#data-freshness-and-history). Try again after the next daily update. On a self-hosted instance, if it persists, check that usage capture is [configured](/self-host/enterprise-features/usage-analytics): an enterprise license, usage storage, and the organization flag.

### A dashboard is empty or missing fields

Check the selected dates, whether the relevant activity occurred after capture began, and whether the nightly refresh has completed. Use **Sync content** when it is offered to update the installed definitions. Sync does not force a data refresh. If a field remains missing after an instance upgrade, contact the Lightdash team.

### Who is “Unknown user”?

The event could not be matched to a name in the current user snapshot. It does not identify a particular type of actor.

Use **Explore from here** and add **User UUID** alongside **User name**. A UUID distinguishes an identified actor whose name is unavailable from activity without a captured user UUID. Inspect **Event name**, **View context**, **Source** or **Actor type** where the Explore provides them. Do not assume every unknown user is an anonymous embed viewer or an AI agent.

A common cause for a row with a **User UUID** is an account with no first or last name set. Add **User email** to see who it is; it shows the account's current primary email, or is empty when unavailable. Set a name on that user's profile, and the row shows it after the next [scheduled refresh](#data-freshness-and-history).

Keep UUIDs in the grouping when two people or content items share a name. You can hide the UUID column in the visualization while retaining separate groups.
