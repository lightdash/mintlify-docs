title: "Warehouse credential setups"
description: "Choose whose warehouse account your team queries as, and who can see which data"

Every query Lightdash runs uses a warehouse account. Your setup decides whose account that is, which decides whether Lightdash or your warehouse controls who sees what, and how much setup people do before they see a chart.

Start with one shared connection. Add optional personal credentials when a few people need their own warehouse permissions. Require personal credentials from everyone only when access or audit by person has to live in the warehouse and your warehouse has a sign-in flow. Split into a project per audience when groups must see different data and don't have warehouse accounts of their own.

## One shared connection

Everyone queries as one warehouse account, set on the [project connection](/integrations/connect-project#choose-how-to-connect-your-warehouse). Use a dedicated read-only account for it, not a person's own sign-in.

**When it fits.** Lightdash roles are enough to decide what people can do, and everyone in the project may see what that account can read. This is the right default for most teams: people see dashboards as soon as they're invited, and scheduled deliveries, embedding, and service accounts work without extra setup.

**The tradeoff.** The warehouse sees one user, so its permissions can't differ by person and its audit logs name only the shared account. Lightdash [roles](/workspace-admin/roles) decide who can explore or open the [SQL runner](/explore/sql-runner). They don't change which tables or rows the warehouse returns, so anyone with `manage:SqlRunner` can query everything the shared account can read. Developers and Admins hold that permission by default. A [custom role](/workspace-admin/custom-roles) can leave it out, but it [can't remove a permission](/workspace-admin/custom-roles#how-additive-permissions-work) someone already has from their organization role.

To narrow what people see without changing the warehouse, use [user attributes](/workspace-admin/user-attributes#using-user-attributes-in-lightdash). They filter rows and hide fields in everything built from the semantic layer, but [raw SQL runs outside them](/agents/agent-access-to-restricted-data#keep-raw-sql-away-from-restricted-roles).

**Warehouses.** All of them.

## Required personal credentials

Each person queries as themselves, so table access, row access, and audit stay in the warehouse. Turn on **Require users to provide their own credentials** in the project's warehouse connection settings, and everyone adds [personal warehouse credentials](/personal-settings/personal-warehouse-connections).

**When it fits.** Access rules already live in the warehouse, you need audit by person, or developers need raw SQL but shouldn't see everything, and your warehouse has a sign-in flow.

**The tradeoff.** Everyone has to add credentials before they can see any data, including people who only view dashboards. A sign-in flow removes most of that work. Without one, each viewer needs a warehouse login issued for them.

Features built around one account also change:

- [Service accounts](/workspace-admin/service-accounts#warehouse-credentials) can't run queries.
- [Embedding](/embed/set-up-embedding) isn't available, because embedded viewers can't provide credentials.
- [Scheduled deliveries](/explore/create-scheduled-deliveries#reassigning-scheduled-delivery-owners) run with their owner's credentials, and fail if the owner's are missing or expired.
- [Pre-aggregates](/semantic-layer/pre-aggregates#not-supported) aren't compatible with personal credentials.
- [Cached results](/semantic-layer/caching#user-level-caching) are stored per person, so one person's query doesn't speed up anyone else's.

**Warehouses.** The setting is on the connection form for BigQuery, Snowflake, Databricks, Redshift, PostgreSQL, Trino, and ClickHouse. The Athena and DuckDB forms don't have it.

Four warehouses have a sign-in flow for [personal credentials](/personal-settings/personal-warehouse-connections#supported-authentication-methods):

- **Snowflake:** **Sign in with Snowflake**, once you [add a security integration](/integrations/connect-project#sign-in-with-snowflake).
- **Databricks:** **Sign in with Databricks**, on instances with Enterprise enabled and an [OAuth application](/integrations/connect-project#sign-in-with-databricks).
- **BigQuery:** **Sign in with Google**.
- **Redshift:** **Sign in with AWS**, through [IAM Identity Center](/integrations/connect-project#redshift). Everyone gets the one permission set fixed on the connection, so it replaces passwords but doesn't give people different access.

Trino, PostgreSQL, and ClickHouse take a username and password.

## Optional personal credentials

A shared connection serves most people, and anyone who adds [personal credentials](/personal-settings/personal-warehouse-connections#when-are-personal-warehouse-credentials-used) queries as themselves.

**When it fits.** Most people view dashboards, and a small group, usually developers or analysts, needs their own warehouse permissions. Where your warehouse supports it, prefer this over requiring credentials: viewers need no setup, and service accounts and embedding keep working on the shared connection.

**The tradeoff.** Personal credentials are opt-in per person, so the shared account stays the boundary for everyone who hasn't added them, SQL runner users included. Scope the shared account to data every project member may see. Two people opening the same dashboard can also get different results, or one can get a warehouse permission error, depending on whose credentials run.

**Warehouses.** Trino and Databricks accept personal credentials whenever **Require users to provide their own credentials** is off. BigQuery does when you also turn on **Use personal credentials when available** in the connection's advanced settings. Other warehouses use personal credentials only when the project requires them.

## A project per audience

Each audience gets its own [project](/workspace-admin/manage-projects), with a warehouse connection scoped to the data that audience may see.

**When it fits.** Groups must see different tables or datasets, and they don't have warehouse accounts of their own. Separate business units or client teams are the usual case.

**The tradeoff.** Each project holds its own spaces, charts, and dashboards, so anything several audiences share exists once per project, and every model change has to reach each one. [Promoting content](/explore/promote-content) copies individual charts and dashboards to another project, but you still keep the copies in step yourself.

A project only separates people whose organization role doesn't reach it. [Organization roles](/workspace-admin/roles#organization-vs-project-roles) above **Member** apply in every project, so keep each audience at **Member** and grant one project role.

**Warehouses.** All of them. Each project can use any of the setups above.

## Add credentials for someone else

If someone can't add their own credentials, an organization admin can [impersonate them](/support/support-access#impersonation-by-your-admins) and add credentials under **Settings** → **My warehouse connections**. Impersonation is off until it's enabled for your organization. Use a password, key, or token issued for that person. A **Sign in with** button saves whichever warehouse account your browser is signed in to, so it would store your identity under their name.

## Service accounts

[Service accounts](/workspace-admin/service-accounts) are for the API and CLI. They have no personal warehouse credentials, so their queries run on the shared connection, and a project that requires user credentials refuses them. If automation has to query a project, use one shared connection or optional personal credentials.

## Pick a setup

Work through these in order and stop at the first answer that settles it:

1. **Do data permissions need to live in the warehouse, as table access, row access, or audit by person?** If Lightdash roles and user attributes are enough, use one shared connection.
2. **Do the groups that need different data lack warehouse accounts of their own?** Use a project per audience.
3. **Do most people view dashboards, or explore and write SQL?** If most view dashboards and your warehouse is Trino, Databricks, or BigQuery, use optional personal credentials.
4. **Does your warehouse have a sign-in flow for personal credentials?** If it does, require personal credentials. If it doesn't, requiring them means issuing a warehouse login to every viewer, so weigh that against a project per audience.
