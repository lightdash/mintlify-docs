Enable the [Lightdash MCP server](/agents/lightdash-mcp) on your self-hosted instance and make its endpoint reachable by your AI clients. This page covers deployment configuration and network access; use the feature documentation for client setup, authentication, tools, and permissions.

## Prerequisites

- **Enterprise license** — `LIGHTDASH_LICENSE_KEY` must be set on your instance.
- **HTTPS** — MCP clients connect over HTTPS. See [secure Lightdash with HTTPS](/self-host/customize-deployment/secure-lightdash-with-https) if your instance is HTTP-only.

## Enable MCP

Set the following environment variable on your Lightdash backend, then restart it:

```bash
MCP_ENABLED=true
```

Lightdash includes the OAuth server; you don't need a separate OAuth service. Organization administrators can still [turn MCP access off](/agents/lightdash-mcp#turn-mcp-access-on-or-off), even when `MCP_ENABLED=true`.

## Optional configuration

<McpEnv />

`run_metric_query` has no separate MCP variable — its row cap is `AI_COPILOT_MAX_QUERY_LIMIT` (default 5000), the same instance-wide setting that limits AI agent queries (see [AI agent environment variables](/self-host/customize-deployment/environment-variables#ai-agents)). It isn't configurable per organization, and a requested limit above the cap is clamped without the response saying so.

To reduce the filter-related query schema sent to the model, enable [compact filter expressions](/self-host/enterprise-features/ai-agents#compact-filter-expressions). That section covers deployment and client-refresh requirements.

## MCP URL format

Once enabled, the MCP endpoint is available at:

```text
https://<your-lightdash-host>/api/v1/mcp
```

Replace `<your-lightdash-host>` with your instance's domain (e.g. `lightdash.yourcompany.com`).

## Connect an AI assistant

Follow [Connect a client](/agents/lightdash-mcp#connect-a-client) to generate configuration using your instance's URL. For headless integrations, see [custom integrations](/agents/lightdash-mcp#custom-integrations).

## Network requirements

If your Lightdash instance sits behind a firewall or VPN, ensure the MCP client can reach it over HTTPS. See the [MCP network requirements](/agents/lightdash-mcp#network-requirements) for additional domains that may need allow-listing depending on the AI assistant.

The client needs `/api/v1/mcp`, the OAuth endpoints under `/api/v1/oauth/`, and the `/.well-known/oauth-*` discovery paths. Some clients connect from their vendor's cloud rather than from the user's machine, so an instance that's only reachable on your internal network works from one client and fails from another. For those clients, allow the vendor's published outbound IP ranges to reach these paths.

Allow more than `GET`: Claude's cloud calls `POST /api/v1/oauth/token` and `POST /api/v1/oauth/register`, and it needs `POST` and `GET` (it opens an SSE stream) on `/api/v1/mcp` itself. A `GET`-only or exact-path allowlist rule lets OAuth discovery pass but leaves the connection stuck after you click **Continue connecting** in Claude.

To check that the endpoint is reachable from a given network, run:

```bash
curl -i https://<your-lightdash-host>/api/v1/mcp
```

A reachable instance returns `401 Unauthorized` with a `WWW-Authenticate` header pointing at your `SITE_URL`. If that URL isn't the public HTTPS address of your instance, OAuth discovery fails. Also check discovery directly:

```bash
curl https://<your-lightdash-host>/.well-known/oauth-authorization-server
```

Its `issuer` and `token_endpoint` should both be your instance's public HTTPS address (`SITE_URL`), not an internal hostname.

### Outbound egress for OAuth client ID metadata documents

Lightdash 2.580.0 and later accepts [OAuth client ID metadata documents](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/) as a way for MCP clients to identify themselves, instead of registering a client first. Claude uses this: it presents an `https` URL as its `client_id`, for example `https://claude.ai/oauth/mcp-oauth-client-metadata`. When a user opens the authorization page for that client, the Lightdash backend fetches the document at that URL itself, over HTTPS, with no redirects and a 5-second timeout — so your backend pods need direct outbound HTTPS access to `claude.ai`, not routed through a proxy that blocks it. If that fetch fails, the authorization page returns `400 Invalid client_id or redirect_uri` instead of the consent page.

<Note>
  Versions 2.580.0–2.589.3 reject client ID metadata documents that advertise extra grant types, which Claude's document does — you need 2.589.4 or later.
</Note>

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `/api/v1/mcp` returns an error or 404 | Check the license and deployment configuration, then confirm **Allow MCP access** is enabled in **Settings** → **MCP** → **General** |
| OAuth flow fails | The Lightdash instance isn't reachable from the browser performing the OAuth redirect |
| AI assistant can't connect | The MCP URL is wrong or the instance isn't accessible over HTTPS |
| Connection hangs after **Continue connecting** | The allowlist only permits `GET` or an exact path on `/api/v1/mcp` — allow `POST` and `GET` on `/api/v1/mcp`, and `POST` on `/api/v1/oauth/token` and `/api/v1/oauth/register` |
| Authorization page returns 400 `Invalid client_id or redirect_uri` | Check you're on Lightdash 2.589.4 or later and that backend pods have outbound HTTPS access to the client's `client_id` host (e.g. `claude.ai`). If `client_id` is an opaque ID rather than a URL, the client registered dynamically instead — check `POST /api/v1/oauth/register` is allowed through and look at the backend logs |
