Self-hosting is great for hobbyist projects or if you want to go wild with a completely custom implementation (maybe you'd prefer the whole app was translated into pirate-speak). For most companies and teams, we recommend Lightdash Cloud.

To self-host Lightdash securely in production, you should have an excellent understanding of running services with Docker and kubernetes, as well as the security considerations.

If you're unsure whether to self-host or use Lightdash Cloud, here are some things to consider:

## When to use Lightdash Cloud

Unless you have a specific need to self-host, we recommend using Lightdash Cloud:

* Suitable for most teams
* Get started with Lightdash quickly
* Secure and reliable out-of-the-box.
* No need to maintain your own infrastructure.
* Always have the latest version of Lightdash.
* Incredible support from the core Lightdash team and maintainers.

### Restrict access by IP address

This isn't self-serve. Contact [Lightdash support](mailto:support@lightdash.com) with the IP addresses or CIDR ranges to allow, and the Lightdash team sets up the restriction on your instance.

The restriction covers your whole instance address together: the web app, login, API, and any embedded content all share the same allowlist. You can't open the API or embeds to everyone while limiting the web app to specific IPs.

Anyone outside the allowed ranges is blocked, including embed viewers and API or MCP clients, so make sure the list includes every client that needs to reach your instance before asking Lightdash to turn it on.

## When to self-host

There are a few reasons why you might want to self-host Lightdash:

* You're a large enterprise and want to run a proof-of-concept on your own infrastructure. This can be a great way to get your hands on Lightdash, while your infosec team approves the use of Lightdash Cloud. For enterprise features on self-hosted instances, see our [enterprise features](/self-host/enterprise-features) documentation.
* You're a hobbyist and want to run Lightdash on your own infrastructure.
* You want to customise Lightdash to your specific needs.

## Move from Lightdash Cloud to self-hosted

Moving an existing Cloud organization to your own instance means running the infrastructure yourself, then copying your content across:

1. Deploy Lightdash following the [production deployment checklist](/self-host/production-deployment-checklist). Enterprise features you use on Cloud, such as embedding, AI agents and data apps, need an [Enterprise license key](/self-host/enterprise-features) on the new instance.
2. Create the project on the new instance and connect the same dbt project and warehouse.
3. Copy charts, dashboards and spaces with `lightdash download` and `lightdash upload` ([content as code](/workflow/content-as-code#download-an-entire-project)), and organization resources such as custom roles, users, groups and user attributes with `lightdash download --organization` and `lightdash upload --organization` ([organization content as code](/workflow/content-as-code#organization-content-as-code)).
4. If you embed Lightdash, [generate an embed secret](/embed/set-up-embedding) and choose the allowed content on the new project. Embed settings aren't part of content as code, and URLs signed with your Cloud secret don't work on the new instance.

## Move from self-hosted to Lightdash Cloud

Moving a self-hosted instance to Lightdash Cloud means setting up a new Cloud project and copying your content across:

1. Create a project on Lightdash Cloud and connect the same dbt project and warehouse you use on your self-hosted instance.
2. Copy charts, dashboards and spaces with `lightdash download` and `lightdash upload` ([content as code](/workflow/content-as-code#download-an-entire-project)), and organization resources such as custom roles, users, groups and user attributes with `lightdash download --organization` and `lightdash upload --organization` ([organization content as code](/workflow/content-as-code#organization-content-as-code)).
3. Recreate any [service accounts](/workspace-admin/service-accounts) on the new Cloud organization and update any CI/CD jobs, deployed services, or scripts to use the new tokens. Service accounts aren't part of content as code, so their secrets don't move with the rest of your content.
