To get the most accurate and useful answers from your AI agents, follow these best practices for preparing your data and configuring your agents.

## Think specialized, not general

Think of AI agents as your specialized analysts - each one can be configured to focus on specific areas of your business. For example, you might create a "Marketing Assistant" that only has access to marketing data like campaign performance, lead generation, and customer acquisition metrics. This focused approach ensures more accurate, relevant responses and prevents sensitive data from being accessible to the wrong teams. To find out more about how to configure specific access, see [Limiting access to specific explores/fields](/agents/data-access#limiting-access-to-specific-explores-and-fields).

Specialized agents also work best with the [AI Router](/agents/enable-ai-router) enabled: the more distinct each agent's focus, description, and data access, the more reliably the router can send each question to the right one — so users don't have to know which agent to ask.

Write an agent description that names its domain, the questions it should receive, and the nearest questions it should not receive. The description helps the router choose an agent; the selected agent's instructions guide how it answers.

## Choose where guidance belongs

Use the narrowest durable scope for each piece of information. This keeps one source of truth and gives the agent the context when it needs it, without adding everything to every prompt.

| If the information… | Put it in… |
| --- | --- |
| Defines a model or field for people and agents | Its semantic-layer [`description`](/semantic-layer/writing-descriptions) |
| Helps only an agent select or query a particular model or field | An [`ai_hint`](/semantic-layer/writing-descriptions#layer-ai-hints-on-top-of-descriptions) next to that semantic object |
| Defines a short term or object-specific rule every agent in the project needs | [`lightdash.project_context.yml`](/agents/agent-context) |
| Describes one agent's role, priorities, defaults, constraints, or answer style | The agent's [instructions](#writing-effective-instructions) |
| Provides longer business reference material the agent should consult when relevant | A [knowledge document](#knowledge-documents) |
| Defines a repeatable procedure for a particular task | A [custom skill](/agents/custom-agent-skills) |
| Determines which agent should receive a question | The agent's description or project [routing instructions](/agents/enable-ai-router#routing-instructions) |

Start with the semantic layer. Give metrics, dimensions, and [parameters](/semantic-layer/parameters) clear names, labels, descriptions, and options. If a colleague could not understand the metadata, an agent is unlikely to interpret it reliably either.

### Understand names and descriptions in YAML

The meaning of `name` and `description` depends on what the YAML defines:

| YAML object | `name` | `description` |
| --- | --- | --- |
| Semantic model or field | Stable identifier visible in metadata. Use `label` for a different human-facing display name. | Shared meaning for people and agents. |
| Agent | Human-facing identity shown in Lightdash. | Routing signal that should state its domain, intended questions, and exclusions. |
| Custom skill | Stable identifier used as its slash command. | Discovery signal that should state what the skill does and when the agent should use it. |

## See the layers in one example

Suppose a Finance agent needs to investigate an unexpected drop in net revenue:

- The metric `description` defines how net revenue is calculated, including its filters and exclusions.
- An `ai_hint` tells the agent that users saying “sales” mean this metric, rather than gross revenue.
- Project context defines a company-specific term such as “board revenue” for every agent in the project.
- The agent description routes Finance reporting questions to this agent and excludes sales-pipeline questions.
- The agent instructions set defaults such as fiscal periods, comparison windows, and communication style.
- A revenue-recognition knowledge document provides the longer accounting policy when the question requires it.
- An `investigate-kpi-change` skill defines the repeatable steps, checks, and expected output for this investigation.

## Avoid conflicts and duplication

Keep each stable fact in one canonical place and link to it instead of copying it into instructions or documents. For example, define what a metric means in its semantic description; let the agent instructions define how answers should be presented.

The only documented precedence rule between these inputs is that an `ai_hint` takes precedence over the semantic `description` in agent prompts. Do not rely on an assumed hierarchy between instructions, knowledge documents, skills, and project context. Remove contradictions, use the narrowest appropriate scope, and test representative questions after changing any layer.

## Knowledge documents

Knowledge documents let you upload longer reference material — glossaries, business policies, supporting context, and internal SOPs — that your agent can consult while answering questions. They live alongside your agent configuration and are a great place to capture material that doesn't belong on one semantic object or in the agent's always-on instructions.

### How they work

When you upload a document, Lightdash reads it and writes a short summary of what it's about — what it covers, which terms it defines, which explores it relates to, and when the agent should consult it. The agent always sees this summary, so it knows the document is available and what's in it. By default, it only reads the full content when a question actually calls for it (**on-demand retrieval**), which keeps conversations fast.

A few things worth knowing:

- **The agent decides when to open a document.** If your document is never being used, the summary probably isn't specific enough about what it's for. Renaming the document or making its purpose clearer in the content usually fixes it.
- **Each document gets a relevance rating against your project.** After uploading, check the relevance card. If a document is rated low or unrelated, the agent has been told not to rely on it for data questions — you'll want to revise it, or scope it to a different agent where it's more relevant.
- **Documents are listed per agent.** The documents table only shows the documents this agent can actually use — organization-level documents (available to every agent) plus any documents specifically granted to this agent. Uploading a document from an agent's settings scopes it to that agent by default.

### Always include in context

For documents the agent should apply to *every* question — not just the ones where the summary happens to match — flip the **Always include in context** toggle in the document's settings panel.

- **On demand (default).** The agent sees only the summary and reads the full document when the question calls for it. Best for large or occasionally-relevant references.
- **Always included.** The full document is embedded into the agent's system prompt on every request. Best for short, high-value context that shapes how *all* answers should be written — for example, a one-paragraph definition of "active customer" that every metric answer should honor.

The documents table shows an **Always included** or **On demand** status chip per document so you can see at a glance which documents will be in every prompt.

<Warning>
Always-included documents make every prompt larger, which uses more tokens and can slow responses. The toggle description surfaces this trade-off in the UI. Keep always-included content short and reserve the toggle for context that genuinely matters on every turn — leave everything else on on-demand retrieval.
</Warning>

Because "always include" changes every future response, switching a document *to* always-included asks for confirmation. Switching back to on-demand retrieval takes effect immediately. Deleting a document also asks for confirmation.

### View, edit, or download a document

#### Open a document

In the agent's knowledge documents list, select the document and click the **View and edit document** (eye) icon to open the fullscreen viewer. Read the document there, or click **Download** to save a copy of the current file.

#### Edit a document

From the document viewer, click **Edit** to change the document. You don't need to delete and re-upload it to fix a typo, refresh guidance, or update frontmatter.

You can edit the document's name and content. Markdown documents open in an editor with a live preview, while plain-text documents open in a monospace text area. YAML frontmatter remains in the raw Markdown source but isn't shown in the preview.

- **Unsaved changes.** Closing the editor with pending changes asks for confirmation. Use **Cancel** to discard changes and return to the viewer.
- **Quotas.** The 20KB per-document and 5MB organization limits also apply to edits. The editor shows the document's size and disables **Save** when the content is over the limit or the name is empty.
- **Summary and context.** When the content changes, Lightdash regenerates the document summary. Saved content is available to the agent on its next message, including for documents that are always included in context.

### What to upload

Good candidates are anything a new analyst on your team would need to read before answering questions, but that doesn't belong in the semantic layer itself:

- **Business glossaries** — definitions of terms like "active customer", "qualified lead", "churn", especially when your definition differs from the industry default
- **Metric provenance and caveats** — "Revenue excludes refunds processed after the period close", "MRR is calculated on the first of the month, not rolling"
- **Fiscal and calendar conventions** — fiscal year start, reporting cadence, holiday adjustments
- **Org-specific acronyms and product taxonomy** — what your internal product codes mean, team naming conventions
- **Known data quirks** — "The `eu_orders` table has a 6-hour ingestion lag", "Pre-2023 data uses the old pricing schema"
- **Policy and escalation context** — when to flag something to a human, which numbers are board-reported and must match a specific source

### What *not* to upload

- **Anything that belongs in the semantic layer.** If it describes a specific field or model, prefer an [AI hint](/semantic-layer/writing-descriptions#layer-ai-hints-on-top-of-descriptions) — those are tied to the field and survive refactors.
- **Sensitive data.** Documents are visible to anyone using the agent. Don't paste API keys, customer PII, or anything you wouldn't share with the whole agent's audience.
- **Raw data dumps.** Knowledge documents are for context and interpretation, not data. The agent has the semantic layer for that.
- **Generic marketing copy or off-topic notes.** These will be rated `low` or `none` relevance and the agent will be told to ignore them.

### Practical tips

- **Keep documents focused and short.** Each document is capped at 20KB and the org-wide quota is 5MB, but the practical limit is much lower: a focused one-page note is consulted more reliably than a sprawling wiki export. Split large references into one document per topic.
- **Use Markdown.** `.md` and `.txt` are supported. Markdown headings and lists make summaries more accurate.
- **Name documents like a `use when` clue.** `Revenue recognition rules.md` is better than `notes.md` — the name is part of what the agent sees.
- **Scope documents per-agent.** A document uploaded for your Finance agent shouldn't pollute your Marketing agent's context. Use the per-agent access setting to keep documents relevant — an agent's documents table only lists the org-level documents plus the ones granted to that agent. For example, a `Refund policy.md` uploaded from the `Analytics Agent` settings is only listed and served to that agent, not to any other agents in the project.
- **Re-check after big changes.** When you add new explores or rename fields, revisit the relevance rating on existing documents — `relatedExploreNames` references exact explore names and can go stale.
- **Test with a real question.** After uploading, ask the agent a question that *should* hit the document and confirm it gets called. The tool calls are visible in the conversation thread.

## Curating verified answers

[Verified answers](/agents/verified-answers) teach your agent from your best examples. To build a set that actually raises answer quality:

-   **Verify diverse examples** - Mark answers covering different types of questions and use cases to give your agent a broad knowledge base

-   **Quality over quantity** - Focus on verifying only your best, most accurate responses. A few excellent examples are better than many mediocre ones

-   **Update regularly** - As your data and business needs evolve, review your verified answers and update them to reflect current best practices

## Making evaluations part of your workflow

<Tip>
Remember: your agent is only as clever as the context and instructions you've given it. For complex data models and diverse use cases, evaluations are essential for systematically testing and refining your agent's performance.
</Tip>

Treat evaluations as an ongoing loop, not a one-off. Encourage your team to use thumbs-up and thumbs-down as they work, build [evaluation suites](/agents/create-evaluation-suites) from the real threads that went wrong, and run them before you ship changes to instructions or your semantic layer — so quality holds as the agent learns and evolves.

## Writing effective instructions

Think of instructions as the agent's always-on operating defaults, not its knowledge base. Use them to define how this agent should approach and communicate every answer.

Focus on four key areas: the agent's role and scope, your team's goals and constraints, how you want data analyzed, and how results should be communicated.

### What to include

- **Role and scope** including the questions the agent should answer and when it should redirect someone elsewhere
- **Communication style** for how results should be presented to your team (e.g., "Keep explanations simple for non-technical stakeholders" or "Always include actionable next steps")
- **Business constraints** like regulatory requirements or budget limitations that affect every analysis this agent performs
- **Analysis preferences** your team relies on (e.g., "Always compare month-over-month growth" or "Flag any churn rates above 5% as concerning")

Put shared terminology in [project context](/agents/agent-context), stable metric definitions in the [semantic layer](/semantic-layer/writing-descriptions), longer supporting material in a [knowledge document](#knowledge-documents), and task-specific procedures in a [custom skill](/agents/custom-agent-skills).

<Check>
  **Good example - Sales Team Agent:** \
   You analyze sales performance for our SaaS company. Focus on MRR, churn, and pipeline health. When MRR growth drops below 10% month-over-month, flag it as concerning. Present insights in simple terms that our sales managers can act on immediately. Always include trend explanations and next steps.
</Check>

### What to avoid

- **Contradictory instructions** that create confusion about priorities
- **Overly complex rules** that are hard to follow consistently
- **Vague guidance** like "be helpful" without explaining what that means for your situation
- **Too many different focus areas** in one agent, remember to keep each agent focused, there are no limits on the number of agents you can create!
- **Restating basic features**, don't tell the AI to "create charts" since it already does that

<Danger>
  **Poor example - Too vague:** \
   Be helpful and analyze data well. Create good charts and explain things clearly.
</Danger>

### Review instructions regularly

As your agent learns from feedback and corrections, its instructions will grow and evolve over time. After extensive agent use, it's helpful to periodically review the instructions in your agent settings to consolidate duplicate guidance and remove outdated preferences or contradictions.
