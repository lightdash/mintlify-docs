A common setup: your aggregate explores are open to everyone, and the record-level explore underneath them is restricted by role with [user attributes](/workspace-admin/user-attributes). Anyone can ask "what was pipeline in EMEA last quarter?", but "which EMEA accounts have open opportunities?" only returns the accounts the person asking is allowed to see.

The catch is that a question can sound aggregate and still run on the restricted explore. "How many open opportunities do EMEA reps have?" is answered from the account grain, so its denominator depends on who asked. This guide covers how to keep that setup governed and make the agent clear about what a number includes.

## Keep the boundary in the semantic layer

Restrict the record-level explore with [`sql_filter`, `required_attributes` or `any_attributes`](/workspace-admin/user-attributes#using-user-attributes-in-lightdash) in the model, not with agent instructions. An agent in its default mode [inherits the asking user's attributes](/agents/data-access#user-attributes-and-permissions) on every query, so one restriction covers Explore, dashboards, and every agent that can see the explore. An instruction like "only show users their own region" is guidance the model can misread, and it does nothing in Explore, so the same user could see different rows in the agent and in Explore.

Use [agent tags](/agents/data-access#limiting-access-to-specific-explores-and-fields) for the other half of the problem: an agent that can't see the record-level explore can't be talked into querying it. A "Regional overview" agent tagged onto the aggregate explores and a separate "Account desk" agent for the restricted one is easier to reason about than one agent that has to know when to be careful.

## Make the agent say who is included

When a number depends on the asking user's attributes, the answer should say so. Someone with a broad role sees the full population, someone with a narrow role sees a subset, and neither is told unless you tell the agent to say it.

Where you put that instruction depends on how many agents need it:

- **One agent:** add it to the agent's [instructions](/agents/set-up-agents#instructions). For example: "Answers from the opportunities explore only cover accounts the person asking can see. Say which population the numbers cover in one clause, such as 'across the accounts you have access to'."
- **Every agent that touches the explore:** add a `context` entry to [`lightdash.project_context.yml`](/agents/agent-context) scoped with `objects` to the restricted explore. Any agent reasoning about that explore picks it up, and it survives agents being added or renamed.

```yaml lightdash.project_context.yml
version: 1
entries:
  - id: opportunities-scope-disclosure
    kind: context
    content: "fct_opportunities is filtered by the asking user's territory attributes. When answering from it, say which population the numbers cover, for example 'across the accounts you have access to'."
    objects: ["fct_opportunities"]
```

Describe the population, not the mechanism. "Across the accounts you have access to" is enough. Attribute names and values are implementation detail that doesn't belong in an answer.

## Treat convenience scopes as their own explores

"My accounts", "my team" and "my open tickets" aren't restrictions. A manager may be allowed to see the whole region and still mean their own book when they say "my". Model the scope explicitly so the agent has something concrete to select instead of guessing the right filter.

The simplest shape is a dedicated explore whose `sql_filter` keys on the asking user's verified email:

```yaml
models:
  - name: my_accounts
    description: Accounts owned by the person asking. One row per account.
    meta:
      sql_filter: ${TABLE}.owner_email = ${lightdash.user.email}
      ai_hint:
        - Use this explore when the user says "my accounts", "my book" or "my customers". It is already filtered to their own accounts; do not add an owner filter.
```

The [`ai_hint`](/semantic-layer/writing-descriptions#layer-ai-hints-on-top-of-descriptions) maps the phrase to the explore. Without it the agent has to guess between `accounts` and `my_accounts`. If ownership lives in another table, a join with [`sql_on`](/workspace-admin/user-attributes#filtering-joins-with-sql%5Fon) that references `${lightdash.user.email}` does the same job. You can't put the reference inside a dimension's own `sql:`. User attributes are [only accepted in `sql_filter`, `required_attributes`, `any_attributes` and `sql_on`](/workspace-admin/user-attributes#using-user-attributes-in-lightdash).

Keep the convenience explore separate from the restricted one. The user's access rules still apply on top of it, so "my accounts" never widens what they can see.

## Keep raw SQL away from restricted roles

In practice: give restricted roles Viewer, Interactive Viewer or Editor, or a [custom role](/workspace-admin/custom-roles) without `manage:SqlRunner`. The agent then follows your semantic layer restrictions for them, whatever its instructions say. Reserve SQL Runner access for the people who own the model. If any of them also need restricting, require personal warehouse credentials on the project.

## Don't build suppression into the semantic layer

It's tempting to go further: hide any result with fewer than five contributing records, mask a column for rows outside the user's team, and so on. Lightdash has no minimum-group-size suppression, and per-row masking of a column isn't possible either, because user attributes can't appear in a dimension's `sql:`. An agent also composes filters freely, so a rule that lives in a handful of metrics doesn't cover the next slice a user asks for.

Stick with the model above: open aggregate explores, and a record-level explore restricted to the roles allowed to see individual records. If one metric genuinely needs a threshold, compute it in dbt so the suppression is fixed in the warehouse regardless of which filters ran, for example a metric that returns null when its group is below the threshold, and expose only that metric on the open explore.
