## Core capabilities

AI agents in Lightdash allow you to:

- **Ask questions in natural language** - Simply type what you want to know about your data, like "What's our total revenue by region?" or "Show me user growth over the last 6 months"
- **Get instant visualizations** - Receive bar charts, time series, and tables automatically generated based on your questions
- **Explore interactively** - Follow up with additional questions, drill down into specific data points, or request different chart types
- **Maintain conversation context** - AI agents remember your conversation history, so you can build on previous questions and refine your analysis
- **Provide text-only responses** - Get answers in natural language when visualizations aren't needed
- **Guide you to the right data** - Direct you to the most relevant explores or tables for your questions
- **Discover existing content** - Find and share relevant charts and dashboards that have already been created in your project
- **Generate complete dashboards** - Create multiple related visualizations at once that tell a cohesive story about your data, perfect for executive summaries or thematic analyses
- **Open pull requests against your project repository** - Ask the agent to rename a metric, add a dimension, or edit a dbt or native Lightdash YAML model and it can open a pull request for review. See [AI writeback](/agents/ai-writeback).
- **Compare across time periods** - Ask for month-over-month, year-over-year, or any custom period offset, and the agent adds a comparison column next to each metric automatically

Lightdash agents use the **semantic layer** defined in your models to understand your data structure, relationships, and business logic.
This ensures that the AI generates accurate queries and visualizations based on your specific data context.
So, *when an Agent generates an answer, the output is a semantic query, **not SQL!*** This means that you can easily swap between the conversational AI interface and the standard Lightdash exploration experience.

## Start a conversation

Open an agent from **Ask AI** to start a new thread. The agent's page shows its name and description above the message input. If the agent has instructions, the info icon beside its name shows them.

Type your question in the message input and click the send button.

### Composer options

The **+** button in the message input opens the composer options. A check mark shows which options are on.

The options you see depend on your permissions and your organization's settings:

- **SQL Runner** turns on [SQL mode](#sql-mode) for the conversation. It appears if you can use the SQL Runner.
- **Deep research** turns your question into a [deep research](/agents/deep-research) run, a long-running investigation that ends in a report. It appears when deep research is enabled and your role can start runs.

### Model and reasoning

When more than one model is available, the model picker beside the send button shows which model answers. Click it to choose another model. For models that support reasoning, the same menu has a **Reasoning** setting with two levels, **Default** and **High**, and the picker shows **High** beside the model name when it is on.

A new conversation starts on the agent's [default model](/agents/set-up-agents#default-model-optional). Admins decide which models appear in the picker; see [Control which models users can pick](/agents/set-up-agents#control-which-models-users-can-pick).

One answer can take several model calls. The agent looks up fields, runs queries and builds charts in separate steps, and each step sends the context gathered so far back to the model. So a question that needs more steps, a long thread, **High** reasoning or a larger model all use more tokens per answer. To see token counts by model and feature, use the **AI usage** explore in the [usage analytics project](/workspace-admin/usage-analytics-project).

When fast mode is available on your instance, the agent hands small routine choices, such as ranking the relevant fields, titling a chart or diagnosing an empty result, to a quick decision model, so simple questions come back faster. There's nothing to train or set up: each decision works from what's in your project when you ask, such as your question, the recent messages in the thread, and the names, labels, descriptions and AI hints of the fields that look relevant. Fast mode doesn't run when your organization or project uses its own [AI provider keys or Bedrock credentials](/agents/set-up-agents#bring-your-own-ai-providers-and-models), or for an agent set to its own **AI provider credential**.

## SQL mode

SQL mode lets the agent reach for raw SQL when a question can't be answered from the semantic layer alone — for example, when the data exists in your warehouse but hasn't been modeled as an explore yet. With SQL mode on, the agent can list warehouse tables, describe their columns, and run SQL queries against your warehouse.

SQL mode can only read data. Lightdash validates every query before it runs and rejects anything that isn't a `SELECT` or `WITH` statement, so mutating or administrative SQL (`INSERT`, `UPDATE`, `DELETE`, DDL) never reaches your warehouse.

SQL mode is **off by default** on every new thread. To turn it on for a conversation, open the [composer options](#composer-options) with the **+** button in the message input and select **SQL Runner**.

### When to use it

- The data you need lives in a warehouse table that isn't part of an explore.
- You want a one-off lookup, audit, or shape-of-the-data check before modeling it.
- The agent has already told you it can't answer from the semantic layer.

Prefer the default (semantic) mode for anything that *can* be answered from your modeled explores — answers stay governed by your dbt metrics, joins, and row-level filters.

### Who can use it

The **SQL Runner** option is visible only to users who hold the **`manage:SqlRunner`** ability — the same permission required to use the [SQL Runner](/explore/sql-runner) page. If you don't see it, ask a workspace admin to grant SQL Runner access to your role.

### How approvals work

SQL mode is gated by a human-in-the-loop check on every query:

1. You turn on SQL mode for the thread.
2. You ask a question. The agent drafts a SQL query.
3. Lightdash shows the proposed SQL inline and waits for you to **Approve** or **Reject** before anything runs against your warehouse.
4. Approved queries return results to the agent, which then summarizes or visualizes them.

Each SQL call is approved individually. To stop the prompts for the rest of a thread, choose **Approve & don't ask again this thread** instead of **Approve**; approvals don't carry over to other threads. [Deep research](/agents/deep-research) and the [Lightdash MCP server's Run SQL tool](/agents/lightdash-mcp#query-execution) don't pause for approval.

### SQL mode in Slack

Slack-triggered prompts can only use SQL mode when your organization has the **\"Require Slack users to authenticate with Lightdash\"** setting (`aiRequireOAuth`) turned on. Without it, Slack messages run under a shared workspace-default identity, so SQL execution is disabled fail-closed whether or not SQL mode is on. See [Slack AI bot setup](/agents/set-up-agents) for how to configure OAuth.

<FeatureBadge label="Beta" /> Some questions need a step after the query: joining two explores, comparing results against a CSV you attach, ranking or bucketing rows, or fitting a forecast. For these, the agent runs one or more queries, then post-processes their results with DuckDB SQL or Python before it answers. It is off by default. [Reach out to us](mailto:support@lightdash.com) to turn it on for your organization.

The semantic layer runs first (or the SQL query, if approved in [SQL mode](#sql-mode)). DuckDB and Python only ever see the rows those queries returned, so metric definitions, joins, [data access](/agents/data-access) rules and SQL approvals apply exactly as they do for any other query. Neither DuckDB nor Python connects to your warehouse.

### How it works

| Step | What it runs | Where it runs |
| --- | --- | --- |
| **Semantic layer** | A metric query against an explore | Your warehouse, through the semantic layer |
| **Warehouse SQL** | A read-only `SELECT` or `WITH` statement, with [approval](#how-approvals-work) | Your warehouse, in [SQL mode](#sql-mode) |
| **DuckDB** | DuckDB SQL over the results of other steps | A sandbox inside Lightdash |
| **Python** | pandas code over the results of other steps | A sandbox inside Lightdash |
| **External data** | DuckDB SQL over a CSV attached to the thread | A sandbox inside Lightdash |

A question that one metric query can answer still runs as a single query. The agent only adds DuckDB or Python steps when the question needs them.

DuckDB and Python both run in a sandboxed environment that only receives the result rows the step references, and is destroyed after each run. Python steps can use pandas, numpy, scipy, pyarrow, scikit-learn and polars. They have no network access and can't install packages.

### Reading the result

The agent shows the result as a card, the same way it shows a chart. Below it, the **Queries** bar shows how many steps ran. Expand it to see each step, grouped into **Sources**, **Transformations** and **Result**, or switch to **Graph** to see how they connect. **View query** shows a step's SQL and **View code** shows a Python step's code. Select a step to see its own rows, and **Back to result** to return.

Opening a result runs the steps as the person viewing it, so viewers only ever see data they have access to.

### Limitations

- A result built with DuckDB or Python lives in its thread. It can't be saved as a chart or added to a dashboard. A result with a single semantic layer step and no post-processing is a regular chart and can be saved.
- Each step is subject to the AI query row limit. A DuckDB or Python step only sees the rows the steps before it returned, so the agent aggregates early when a step would hit its limit.

## Query execution stats

When an agent runs a query against BigQuery, it gets the warehouse's statistics for the job back with the results. You can ask the agent how much data a query scanned or how long it took. For example: "How many bytes did that query process?"

| Stat | What it means |
| --- | --- |
| Bytes processed | Data BigQuery read to run the query |
| Bytes billed | Data BigQuery billed for the query, after its rounding and minimums |
| Execution time | Time from job start to job end, as reported by BigQuery |
| Warehouse cache hit | Whether BigQuery served the job from its own result cache |
| Job ID | The BigQuery job ID, for looking the job up in the BigQuery console or `INFORMATION_SCHEMA.JOBS` |

The stats cover metric queries and SQL mode queries. They are not reported when:

- The results come from the [results cache](/semantic-layer/caching). No warehouse job runs, so there is nothing to report.
- The project uses a warehouse other than BigQuery.

## Response time

Each agent reply shows how long it took, as time to first token and total time. Hover over it for a breakdown of where that time went:

| Stage | What it covers |
| --- | --- |
| Prep | Loading context, the explore catalog, and tools before the model starts |
| Provider | Time the model provider spent generating. Shows `n/a` when the provider doesn't report it separately |
| Query | Running queries against your warehouse |
| API | Other tool calls, such as searching fields or content |
| Render | Building charts, dashboards, apps, and exports |

When they apply, the tooltip also counts queries served from the [results cache](/semantic-layer/caching) and queries that reused an earlier verified result. Times are measured on the server, and stages that run at the same time can overlap, so they don't always add up to the total.

## Asking about a chart or dashboard

You can launch an AI conversation with a chart or dashboard pre-loaded as context. From the resource's `⋯` menu, click **Ask AI Agent**.

This opens a new tab on the new-thread page for your default agent. The chart or dashboard appears as a **pinned context card** above the input, and the agent treats it as the subject of the conversation.

### Pinned context

- The pinned card stays visible above your message in the thread, so anyone reading later can tell what was being discussed.
- Click the pinned card to open the chart or dashboard in a new tab.
- The pinned context persists across follow-up messages — *"now break it down by region"* still refers to the originally pinned chart.

### Linked dashboard

A thread created through the API or the React SDK can be bound to a dashboard for its whole life, which you can't change afterwards. Pinned context belongs to one message; a binding belongs to the whole thread. See [Bind a thread to a dashboard](/embed/embed-ai-agents#bind-a-thread-to-a-dashboard) for how to create one.

- A **Linked dashboard** card at the top of the thread opens the dashboard. The thread never pins a different dashboard from the page you're on, and `@` tile mentions come from the linked dashboard.
- If the agent can create content, it can only change the linked dashboard and the charts saved in it. See [Threads bound to a dashboard](/agents/enable-content-tools#threads-bound-to-a-dashboard).
- If the thread was created with background context, admins see it in a collapsed **Thread context** block. Other users don't see it, but the agent always uses it. Custom roles can grant the `view:AiAgentThreadContext` scope to show it.
- If the dashboard is deleted, the card shows **Dashboard no longer available**. You can keep asking questions, but the agent can't change saved content in that thread.

### Mentioning dashboard tiles

When the pinned context is a dashboard, you can `@`-mention any of its chart tiles directly in your message to focus the agent on a single tile.

Type `@` in the input and pick a tile from the **Dashboard tiles** group in the suggestion list. The selected chart is added alongside the pinned dashboard, so the agent answers about that specific tile while still keeping the dashboard as overall context.

This is useful when a dashboard has many charts and you want to drill into one without leaving the thread:

- *"Why did @Weekly active users drop last week?"*
- *"Break @Revenue by region down by channel."*

### What you can ask

When you pin a saved chart, the agent can read its actual data (subject to your [data access setting](/agents/data-access)). It honors the chart's saved filters, sorts, custom metrics, and [parameter values](/semantic-layer/parameters), so you can ask:

- *"Why is this trending up?"*
- *"Are there outliers in this chart?"*
- *"Compare this chart's last 30 days to the previous period."*

If your agent has data access disabled, pinning still works — the agent sees the chart's structure (name, dimensions, metrics) but no row values are sent to the underlying LLM.

## Mentioning charts and dashboards with `@`

You can reference saved charts and dashboards directly from the chat input by typing `@`. This adds them as context for the agent's next message, similar to a pinned card, without leaving the conversation.

Type `@` followed by part of a name to open the suggestion menu. Suggestions are grouped so the most relevant content appears first:

- **Already mentioned** — content already referenced earlier in this thread.
- **Current page** — the chart or dashboard you're viewing when you open the chat.
- **Dashboard tiles** — charts on the dashboard you're currently viewing.
- **Search results** — any chart or dashboard you have access to, ranked by your search query. [Verified content](/explore/verified-content) is marked with a green check.

Use the arrow keys to highlight a suggestion and press `Enter` or `Tab` to insert it. While the menu is open, `Enter` selects the suggestion instead of sending the message.

Each mention becomes a chip in the input — for example, `@Weekly revenue` — and travels with the message as prompt context. The agent uses the same access rules as a pinned card: it can read the resource's structure and (when [data access](/agents/data-access) is enabled) its underlying data.

<Tip>
  Mention multiple resources in a single message to ask comparative questions, such as *"How does @Weekly revenue compare to @Marketing dashboard's signups trend?"*
</Tip>

You can only mention content you have permission to view. Mentions are available in agent threads, in the AI Router, and in the launcher used to start new threads.

## Read-only threads

In some cases, the chat input on an existing thread is disabled and you can't send follow-up messages. The input shows a short message explaining why. You'll see this when:

- **The thread was started in Slack.** Reply in the original Slack thread to continue the conversation.
- **The thread belongs to another user.** You can read the conversation, but only the original author can post follow-ups.
- **The model used in the thread is no longer available.** Threads are pinned to the model that produced the first assistant response, so the conversation history stays consistent. If an admin removes that model from the agent — or the provider no longer offers it — start a new thread to continue with one of the agent's current models.

To start a new thread, open the agent and click **New thread**.

## Share a thread

To let a colleague continue from your conversation, click the **Share thread** icon in the thread header and copy the link. Anyone with the link who can use the agent and start threads opens the conversation as their own copy, and can continue it independently. The copy includes the conversation up to the moment you created the link; messages you send afterwards aren't included.

The **Share thread** icon appears on threads started in the Lightdash app or through the API, not on threads started in Slack. Sending the thread's own URL instead only works for you and for users who can manage the agent, such as project developers and admins, who can read it but not reply (see [Read-only threads](#read-only-threads)).

## Delete a thread

To delete one of your threads, open its menu in the agent's thread list and click **Delete**. Deletion is permanent and also removes the thread's tool calls and the memories the agent learned from it. You need the Editor role or higher in the project.

Threads started in Slack can't be deleted from the thread list, because that wouldn't remove the messages from Slack. People who manage the project's agents, such as project admins and developers, can delete any thread there, Slack ones included, from **Settings** → **Ask AI** → **Threads**. To delete threads automatically after a period of inactivity, see [Thread retention](/agents/thread-retention).

## Schedule a recurring delivery from a conversation

When an agent lands on an answer worth watching, you can turn that conversation into a recurring [scheduled delivery](/explore/create-scheduled-deliveries). Lightdash re-runs the agent on your chosen frequency and sends the refreshed chart, along with an AI-written summary, to Slack, email, or Microsoft Teams.

Open the `⋯` **Quick actions** menu on a saved chart the agent produced and choose **Schedule delivery**.

## Example use cases

### Period-over-period comparisons

Agents can answer time-comparison questions directly — month-over-month, year-over-year, or any custom offset — without you having to set up the comparison in the Explorer first.

When you ask a comparison question, the agent picks a base metric, a time dimension, a granularity (day, week, month, quarter, or year), and an offset (how many periods back). It then runs the query and adds a comparison column next to the base metric, labelled with the offset (for example, `Revenue (Previous month)`).

**Prompts that work well**

- *"Compare revenue to last month"*
- *"Month-over-month new users"*
- *"Year-over-year orders by week"*
- *"Show revenue this quarter vs the previous quarter, and vs the same quarter last year"*

You can stack multiple comparisons on the same metric (for example, MoM and YoY together) and you can use a [custom metric](/explore/create-custom-fields) as the base.

<Tip>
  Period-over-period is for comparing whole prior periods (last month, last quarter, last year). For period-to-date questions like MTD or YTD, ask the agent for a filtered aggregation instead — for example, *"revenue so far this month vs the same point last month"*.
</Tip>

**Limitations**

- The granularity must match the time dimension's interval — ask for *"monthly revenue vs last month"* (not *"daily revenue vs last month"*).
- The agent can't yet sort or filter on the generated comparison column directly; sort or filter on the base metric or the time dimension instead.

## FAQs

1. Does Lightdash store the query data?

Lightdash stores each conversation, your questions and the agent's replies, so you can look back at it, along with the query definitions behind its charts and tables. It keeps threads until they're deleted or a [thread retention](/agents/thread-retention) window expires them. The actual data and detailed results stays in your warehouse and gets pulled fresh when the results are revisited (unless data access is enabled).

The agent's written reply is saved as it was written and isn't recomputed. If your data or models change between the conversation and when you revisit it, a chart or table in the thread can show different numbers from the text around it.

2. Can I assign a default agent?

You can assign your default agent in Ask AI by clicking the star by your agent's name.

The default agent setting is per-user, per-project. There's no project-wide default at the moment.

When you have a default agent set, Ask AI opens it directly — even if the [AI Router](/agents/enable-ai-router) is enabled.

If you haven't set a default and the AI Router is enabled, Lightdash routes each question to the best-fit agent automatically. If the router is off and you have no default, Ask AI opens the first agent in the project's list, sorted alphabetically by agent slug (not by creation date).

To steer everyone without a personal default toward one agent, enable the AI Router and add [routing instructions](/agents/enable-ai-router#routing-instructions) such as *"Use @general-agent unless the question is about billing."*

## Known limitations


### Data analysis and calculations

AI agents can query your actual data through metric queries, field value search, and [SQL mode](#sql-mode), and can define [custom metrics](/explore/create-custom-fields) and formula [table calculations](/explore/table-calculations) on the fly. For forecasts, regressions and other statistical work, agents can [post-process results with DuckDB and Python](#post-process-results-with-duckdb-and-python). Reading result rows is subject to your [data access setting](/agents/data-access).

### Query and visualizations constraints

Results are limited by configurable query limits set at server level to ensure good performance. These limits can only be adjusted through environment variables at the moment.

When you ask an agent to join data across two explores that have no join defined in your dbt models, it runs the join as a merge — the same mechanism behind the Explorer's **Merge another query** flow. Each side runs as its own query capped at the configured query limit, and Lightdash joins the results afterwards; if a side is cut off by its limit, the merge fails rather than returning a partial join. See [How a merge runs](/explore/merge-queries#how-a-merge-runs) and [Row limits](/explore/merge-queries#current-limits) for the full mechanics.

A join defined in your dbt models doesn't go through this path: the agent's metric query pushes the whole join down to your warehouse as a single query, so it isn't subject to this per-side limit. If a pair of explores hits the merge limit often, model the join between them in dbt instead.

Agents can create tables, bar charts, vertical bar charts, line charts, scatter plots, pie/donut charts, and funnel charts, but don't yet support [custom visualizations](/visualizations/custom-charts) or big number charts.

### Data access and context

Agent access to your data is controlled through tags in your dbt models and by the asking user's user attributes. If certain fields aren't accessible, check that they have the appropriate tags assigned to your agent, and that the user's attributes allow them. See [Who can see what](/agents/data-access#who-can-see-what) for how the controls stack, including [SQL mode](#sql-mode).

Agents don't remember context between different conversation sessions. Each chat starts fresh.

When an agent can use 15 or fewer explores, Lightdash includes the list of them in the agent's context. With more than 15, the agent searches for the fields it needs instead.
