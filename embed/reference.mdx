## Overview

This document provides complete API reference for JWT structure and configuration options used across all embedding and sharing methods.

Lightdash supports three ways to share embedded content:
- **Shareable URL** — Generate a link that anyone can open directly in their browser, no iframe or SDK needed. Ideal for sharing dashboards with external users like clients or partners.
- **iframe embedding** — Embed dashboards inside your own web pages using a standard `<iframe>` tag.
- **React SDK** — Embed dashboards and charts in React/Next.js apps with full programmatic control.

All three methods use the same JWT-based authentication described below.

For role-controlled dashboard capabilities and AI access, see [Permission modes](#permission-modes).

**For method-specific implementation details, see:**
- [iframe embedding reference](/embed/iframe) - URL patterns, HTML embedding
- [React SDK reference](/embed/react-sdk) - React components, props, TypeScript

**For step-by-step guides, see:**
- [Embedding quickstart](/embed/set-up-embedding)
- [Embedding dashboards](/embed/embed-dashboards)
- [Embedding charts](/embed/embed-charts)

Embedded Lightdash content is available to view by anyone (not just folks with a Lightdash login). Content is secured using JWT (JSON Web Tokens) with configurable expiration times.

Embeds don't link to the Lightdash documentation or offer to share errors with Lightdash support, and their labels and error messages don't name Lightdash. React SDK components never change your page's document title.

## Known limitations

- Embedding works for dashboards, charts, [AI agents](/embed/embed-ai-agents), the [metrics catalog](/embed/embed-metrics-catalog), and [data apps](/data-apps). To embed explores, use the `canExplore` flag in a dashboard or metrics catalog token.
- The **Filter dashboard to** option when clicking on individual chart segments will not work on embedded dashboards.

If you're interested in embedding and one or more of these items are blockers, please reach out.

## Embed secret

The embed secret is used to generate JWTs for embedding content. This secret acts like a password that encrypts and signs your tokens.

<Frame>
  ![Project settings on the Embed configuration tab, showing an empty "No embed secret" state with a Generate embed secret button](/images/embed/embed-create-secret-fbb86d6bcb70f4d004c48adb3c107922.png)
</Frame>

<Warning>
Keep your embed secret secure! Store it as an environment variable and never expose it in frontend code. Always generate tokens server-side.
</Warning>

You can regenerate the secret by clicking `Generate new secret`. If you do this, all previously generated embed URLs will be invalidated immediately.

## JWT structure

All embedding methods use JWTs to authenticate and configure embedded content. The token structure includes three main parts:

### Common fields

All tokens share these fields:

```typescript
{
  content: {
    // Content configuration (required)
    type: 'dashboard' | 'chart' | 'aiAgent' | 'metricsCatalog' | 'dataApp' | 'apiAccess',
    projectUuid?: string,
    // ... type-specific fields
  },
  user?: {
    // User information for analytics (optional)
    externalId?: string,
    email?: string,
  },
  userAttributes?: {
    // User attributes for row-level filtering (optional)
    [attributeName: string]: string,
  },
  // Token expiration (handled by JWT library)
  exp?: number,
  iat?: number,
}
```

### Dashboard token

For embedding dashboards with multiple tiles, filters, and interactive features.

<Warning>
All configuration options (`dashboardFiltersInteractivity`, `canExportCsv`, `canExplore`, etc.) must be nested **inside the `content` object** — not at the top level of the JWT payload. A common mistake is placing these properties at the root level, which will cause them to be silently ignored.
</Warning>

```typescript
{
  content: {
    type: 'dashboard',

    // Dashboard identifier (required, use one)
    dashboardUuid?: string,
    dashboardSlug?: string,

    // Project identifier (optional)
    projectUuid?: string,

    // Filter interactivity
    dashboardFiltersInteractivity?: {
      enabled: 'all' | 'some' | 'none',  // Required
      allowedFilters?: string[],          // Required if enabled: 'some'
      hidden?: boolean,                   // Optional: hide filter UI
      canAddFilters?: boolean,            // Optional: let viewers add temporary filters
    },

    // Parameter interactivity
    parameterInteractivity?: {
      enabled: boolean,
    },

    // Export capabilities
    canExportCsv?: boolean,         // Allow per-chart CSV export
    canExportDashboardCsv?: boolean, // Allow dashboard CSV/XLSX ZIP export
    canExportImages?: boolean,      // Allow image/PNG export
    canExportPagePdf?: boolean,     // Allow PDF export

    // Interactive features
    canDateZoom?: boolean,          // Allow date granularity zoom
    canExplore?: boolean,           // Allow "Explore from here"
    canViewUnderlyingData?: boolean, // Allow viewing raw data
    canViewDataApps?: boolean,      // Allow rendering data app tiles
  },

  // Optional: Allow embedded users to save charts and edit dashboards
  writeActions?: {
    writeSpaceUuids: string[],        // Spaces users can write to; the first is the default
    sourceSpaceUuids?: string[],      // Extra spaces to add existing charts from
    serviceAccountUserUuid?: string,  // Actor for the write (use one)
    userUuid?: string,
    permissionsMode?: 'default' | 'roles',
  },

  // Optional: User information for query tracking
  user?: {
    externalId?: string,
    email?: string,
  },

  // Optional: User attributes for row-level filtering
  userAttributes?: {
    [attributeName: string]: string,
  },
}
```

**Example:**

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'dashboard',
    dashboardUuid: 'abc-123-def-456',
    dashboardFiltersInteractivity: {
      enabled: 'all',
    },
    canExportCsv: true,
    canExportImages: true,
    canExportPagePdf: true,
    canDateZoom: true,
    canExplore: true,
    canViewUnderlyingData: true,
    canViewDataApps: true,
  },
  user: {
    externalId: 'user-789',
    email: 'user@example.com',
  },
  userAttributes: {
    tenant_id: 'tenant-abc',
  },
}, SECRET, { expiresIn: '1h' });
```

### Chart token

For embedding individual saved charts with minimal UI:

<Warning>
Chart embedding is **only available via the React SDK**. iframe embedding for charts is not currently supported. See the [React SDK reference](/embed/react-sdk) for details.
</Warning>

```typescript
{
  content: {
    type: 'chart',

    // Chart identifier (required)
    contentId: string,  // savedQueryUuid

    // Project identifier (optional)
    projectUuid?: string,

    // Preview mode (optional)
    isPreview?: boolean,

    // Permission scopes (optional)
    scopes?: string[],  // e.g., ['view:Chart']

    // Export capabilities
    canExportCsv?: boolean,         // Allow CSV export
    canExportImages?: boolean,      // Allow image/PNG export
    canViewUnderlyingData?: boolean, // Allow viewing raw data
  },

  // Optional: let viewers edit and drill into the chart with Lightdash.Chart isEditMode
  writeActions?: {
    writeSpaceUuids: string[],        // Must include the chart's space
    serviceAccountUserUuid?: string,
    userUuid?: string,
  },

  // Optional: User information for query tracking
  user?: {
    externalId?: string,
    email?: string,
  },
}
```

Chart tokens use `contentId` (the saved chart UUID) instead of `dashboardUuid`, and the embed is scoped to that chart alone — it cannot reach any other content.

**Example:**

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'chart',
    contentId: 'saved-chart-uuid-789',
    scopes: ['view:Chart'],
    canExportCsv: true,
    canExportImages: false,
    canViewUnderlyingData: true,
  },
  user: {
    externalId: 'user-456',
    email: 'user@example.com',
  },
}, SECRET, { expiresIn: '24h' });
```

### AI agent token

For embedding a Lightdash [AI agent](/agents) so users can chat with their data from inside your app. See [Embedding AI agents](/embed/embed-ai-agents) for the full walkthrough.

```typescript
{
  content: {
    type: 'aiAgent',

    // Agent the embed is allowed to use (required)
    agentUuid: string,

    // Project identifier (optional)
    projectUuid?: string,

    // Allow "Explore from here" inside the embed (optional)
    canExplore?: boolean,

    // Show the Debug panel on agent answers (optional, defaults to false)
    canViewDebugInfo?: boolean,
  },

  // Required: AI agent embeds must include writeActions
  writeActions: {
    writeSpaceUuids: string[],          // Spaces the agent reads from and saves to; the first scopes threads
    sourceSpaceUuids?: string[],        // Extra spaces the agent can read and search, but not create or update content in
    serviceAccountUserUuid?: string,    // Use a service account as the actor
    userUuid?: string,                  // Or use an existing Lightdash user as the actor
    permissionsMode?: 'default' | 'roles',
  },

  // Optional: row-level filtering for the embedded viewer
  userAttributes?: {
    [attributeName: string]: string,
  },

  // Optional: viewer identity. Not a query tag for agent queries, see User metadata
  user?: {
    externalId?: string,
    email?: string,
  },
}
```

<Info>
AI agent tokens are scoped to a single agent. A token issued for one `agentUuid` cannot be used to access another agent, and dashboard or chart tokens are rejected on AI agent routes. The agent can read dashboards and saved charts from the token's write spaces and any `sourceSpaceUuids`, and saves new charts into one of the write spaces. Embedded viewers can open saved charts from that combined scope in the chat side panel and saved dashboards as a read-only view, with the token's `userAttributes` applied. Threads are scoped to the first write space; see [Embedding AI agents](/embed/embed-ai-agents#access-control).
</Info>

**Example:**

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'aiAgent',
    projectUuid: 'your-project-uuid',
    agentUuid: 'your-agent-uuid',
  },
  writeActions: {
    serviceAccountUserUuid: 'service-account-user-uuid',
    writeSpaceUuids: ['destination-space-uuid'],
  },
  userAttributes: {
    tenant_id: 'tenant-abc',
  },
  user: {
    email: 'customer@example.com',
  },
}, SECRET, { expiresIn: '1h' });
```

### Metrics catalog token

For embedding the project [metrics catalog](/semantic-layer/metrics) so embedded users can browse metrics and, optionally, continue into Explore. See [Embedding the metrics catalog](/embed/embed-metrics-catalog) for the full walkthrough.

```typescript
{
  content: {
    type: 'metricsCatalog',

    // Project identifier (required — pins the catalog to a single project)
    projectUuid: string,

    // Allow embedded users to open Explore from a metric (optional)
    canExplore?: boolean,
  },

  // Optional: enable saving charts from the embedded Explore. Required only
  // when canExplore is true and you want embedded users to save results.
  writeActions?: {
    writeSpaceUuids: string[],
    serviceAccountUserUuid?: string,
    userUuid?: string,
  },

  // Optional: row- and column-level filtering for the embedded viewer
  userAttributes?: {
    [attributeName: string]: string,
  },

  // Optional: user information surfaced in audit/analytics
  user?: {
    externalId?: string,
    email?: string,
  },
}
```

<Info>
Metrics catalog tokens only authorize the metrics catalog surface (and, when `canExplore` is `true`, the embedded Explore launched from a metric). Dashboard, chart, AI agent, and data app tokens are rejected by the metrics catalog routes, and metrics catalog tokens are rejected on other embed routes.
</Info>

**Example:**

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'metricsCatalog',
    projectUuid: 'your-project-uuid',
    canExplore: true,
  },
  writeActions: {
    serviceAccountUserUuid: 'service-account-user-uuid',
    writeSpaceUuids: ['destination-space-uuid'],
  },
  userAttributes: {
    tenant_id: 'tenant-abc',
  },
  user: {
    email: 'customer@example.com',
  },
}, SECRET, { expiresIn: '1h' });
```

### Data app token

For embedding a [data app](/data-apps) as standalone content in an iframe (no dashboard). See [How to embed data apps](/embed/embed-data-apps) for the full guide.

```typescript
{
  content: {
    type: 'dataApp',

    // Data app identifier (required)
    appUuid: string,

    // Project identifier (optional)
    projectUuid?: string,

    // Preview mode (optional)
    isPreview?: boolean,
  },

  // Optional: User information for query tracking
  user?: {
    externalId?: string,
    email?: string,
  },

  // Optional: User attributes for row-level filtering
  userAttributes?: {
    [attributeName: string]: string,
  },
}
```

A `dataApp` token authorizes only the named app. It cannot render any other data app, chart, or dashboard, even if that content is on the embed allowlist, and interactivity options like `canExportCsv`, `canExplore`, and `dashboardFiltersInteractivity` do not apply to it.

<Warning>
A data app can run arbitrary metric queries across the project. Minting a `dataApp` token means accepting project-wide column access for the app's queries. Row-level access via [user attributes](/workspace-admin/user-attributes) is unchanged.
</Warning>

**Example:**

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'dataApp',
    projectUuid: 'your-project-uuid',
    appUuid: 'your-app-uuid',
  },
  user: {
    externalId: 'user-789',
    email: 'user@example.com',
  },
  userAttributes: {
    tenant_id: 'tenant-abc',
  },
}, SECRET, { expiresIn: '1h' });
```

### API access token

Use an API access token when your host app needs to call Lightdash APIs through the React SDK, for example to list spaces, dashboards, and charts with [`Lightdash.useLightdashContent`](/embed/react-sdk#lightdashuselightdashcontent).

```typescript
{
  content: {
    type: 'apiAccess',

    // Project identifier (required)
    projectUuid: string,

    // Service account used for permission checks (required)
    serviceAccountUserUuid: string,
  },

  // Optional: row-level filtering for APIs that evaluate user attributes
  userAttributes?: {
    [attributeName: string]: string,
  },

  // Optional: user information surfaced in audit/analytics
  user?: {
    externalId?: string,
    email?: string,
  },
}
```

<Info>
API access tokens do not embed a specific dashboard or chart. They let the React SDK call supported Lightdash API endpoints with the permissions of `serviceAccountUserUuid`.
</Info>

**Example:**

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'apiAccess',
    projectUuid: 'your-project-uuid',
    serviceAccountUserUuid: 'service-account-user-uuid',
  },
  userAttributes: {
    tenant_id: 'tenant-abc',
  },
  user: {
    externalId: 'customer-user-123',
    email: 'customer@example.com',
  },
}, SECRET, { expiresIn: '1h' });
```

**Rules:**

- API access tokens must be generated server-side with your embed secret.
- API access is authorized through the service account. The token can only list or read content that the service account can access.
- A space UUID passed to an API hook is a filter, not a permission grant.
- API access tokens cannot perform embed write actions. Use an embed token that supports `writeActions` when embedded users need to save charts or dashboards.

## Interactivity options reference

The options below describe JWT-controlled interactivity. For dashboard role-based grants, see [Permission modes](#permission-modes).

### Dashboard filters interactivity

Controls whether users can interact with dashboard filters.

```typescript
dashboardFiltersInteractivity?: {
  enabled: 'all' | 'some' | 'none',
  allowedFilters?: string[],  // Filter UUIDs, required if enabled: 'some'
  hidden?: boolean,           // Hide filter UI but keep filters active
  canAddFilters?: boolean,    // Let viewers add temporary session-only filters
}
```

**Options:**

- `enabled: 'all'` - All dashboard filters are visible and interactive
- `enabled: 'some'` - Only filters listed in `allowedFilters` are interactive
- `enabled: 'none'` - Filters are applied but not visible or editable
- `hidden: true` - Filters are configurable at runtime, but UI is hidden (works with 'all' or 'some')
- `canAddFilters: true` - Render an **Add filter** button so viewers can add temporary filters over any filterable field in the dashboard's explores. Only effective when filter interactivity is enabled (`enabled: 'all'`, or `enabled: 'some'` with a non-empty `allowedFilters`). Viewer-added filters live in session state and the temp-filter deep-link parameter — a fresh embed URL starts clean. JWTs without this field behave exactly as before (button hidden). Metric filters in the picker still require the `metric-dashboard-filters` feature flag on the org.

<Info>
Embed overrides targeting a [locked dashboard filter](/explore/dashboards/filter#locking-dashboard-filters) are ignored, and the dashboard's saved locked value is used instead. Use a locked filter when you need to guarantee an embedded dashboard always runs with a specific value — for example, scoping every query to the customer who owns the embed session.
</Info>

#### All filters available as interactive:

All filters configured on the dashboard will be shown in the embedded dashboard and interactive.

```javascript
dashboardFiltersInteractivity: {
  enabled: 'all',
}
```

#### Let viewers add their own filters:

Set `canAddFilters: true` to render an **Add filter** button in the embedded filter bar. Viewers can add temporary filters against any filterable field in the dashboard's explores. These filters live only in session state and the temp-filter deep-link parameter — reopening the embed URL clears them, and they are never saved back to the dashboard.

```javascript
dashboardFiltersInteractivity: {
  enabled: 'all',
  canAddFilters: true,
}
```

The Add filter button only renders when filter interactivity is enabled (`enabled: 'all'`, or `enabled: 'some'` with a non-empty `allowedFilters`). Omitting `canAddFilters` preserves the existing behavior (button hidden).


### Parameter interactivity

Controls whether users can modify dashboard parameters.

```typescript
parameterInteractivity?: {
  enabled: boolean,
}
```

When enabled, users can change parameter values in the dashboard UI.

### Export options

Control what users can export from embedded content.

```typescript
{
  canExportCsv?: boolean,        // Download chart data as CSV files
  canExportImages?: boolean,     // Download charts as PNG images
  canExportPagePdf?: boolean,    // Download the dashboard as PDF (dashboards only, on unless false)
}
```

**CSV Export:**
- Enables "Download CSV" in chart tile menus
- Each chart can be exported individually
- Exports the data shown in the visualization

<Frame>
  ![A table tile's menu open over the results, offering a single Download option](/images/embed/reference/embedding-download-csv-2a4cbcfa350c6cefed880971090c117b.png)
</Frame>

**Image Export:**
- Enables "Download as image" in chart tile menus
- Exports charts as PNG files
- Captures current chart state

In an Explore opened with **Explore from here**, the same two options enable downloads from the chart and results panels. Google Sheets export is not offered in embeds.

**PDF Export (dashboards only):**

PDF export is on unless the token sets `canExportPagePdf: false`; in [`'roles'` mode](#dashboard-capabilities) it needs `view:EmbedPagePdfExport` instead. What the icon button in the dashboard header does depends on how the dashboard is embedded:

| Embed method | Tooltip | Output |
| --- | --- | --- |
| React SDK | **Export as PDF** | A PDF rendered by Lightdash with only the dashboard: every visible tab stacked in order, using the viewer's current filters, parameters, and date zoom |
| iframe | **Print this page** | The browser's print dialog for the embedded page |

The SDK export doesn't apply the component's `paletteUuid` or `contentOverrides`. Self-hosted instances need [object storage](/self-host/customize-deployment/configure-lightdash-to-use-external-object-storage) and the [headless browser](/self-host/customize-deployment/enable-headless-browser-for-lightdash) for it.

### Export all dashboard tiles

Set `content.canExportDashboardCsv: true` to show **Export all tiles** in the embedded dashboard header. Viewers can choose **Export all as .csv (.zip)** or **Export all as .xlsx (.zip)** to download the dashboard's chart tiles in a ZIP archive.

This option is off by default and independent of `canExportCsv`, which controls per-chart CSV downloads. It applies only to the dashboard identified by the embed token. In scope-based embed permissions, the corresponding scope is `view:EmbedDashboardCsvExport`.

Exports use formatted values, each chart's table row limit, and pivoted results. They apply the current dashboard filters, date zoom, and parameter values. The embedded export menu uses these defaults without an export-options dialog.

### Date zoom

Allows users to zoom into time-series data by changing granularity.

```typescript
canDateZoom?: boolean
```

When enabled, the embed renders the dashboard's configured date zoom controls (the Default zoom plus any named controls), letting users change the date granularity of charts on the dashboard. See the [Date zoom guide](/explore/dashboards/date-zoom) for complete documentation on this feature.

### Explore from here

Enables navigation from dashboard charts to the explore view.

```typescript
canExplore?: boolean
```

When enabled, users see "Explore from here" in chart tile menus. This opens the full query builder with the chart's configuration pre-loaded.

<Frame>
  ![A bar chart tile's menu open, offering "Explore from here"](/images/embed/reference/embedding-explore-from-here.png)
</Frame>

Users can:
- Modify dimensions and metrics
- Apply different filters
- Change chart types
- Run custom queries

The `canExplore` option alone does not allow users to save charts, share results, or view SQL. Downloads follow `canExportCsv` and `canExportImages`. To let users save charts from Explore, configure a [writeActions claim](#write-actions). Saving from **Explore from here** always creates a new chart; it never overwrites the chart the user started from.

### View underlying data

Allows users to view the raw data table behind visualizations.

```typescript
canViewUnderlyingData?: boolean
```

When enabled, users can click on charts to open a modal showing the underlying data table. Data cannot be exported separately (use `canExportCsv` for that).

<Frame>
  ![A "View underlying data" option floating over a clicked bar in a bar chart](/images/embed/reference/embedding-view-underlying-data.png)
</Frame>

### View data apps

Allows [data app](/data-apps) tiles on an embedded dashboard to render and run their metric queries.

```typescript
canViewDataApps?: boolean
```

Data app tiles run arbitrary metric queries against your semantic layer, so they need broader access than a standard chart tile. Enabling `canViewDataApps` grants the embed JWT the additional permissions a data app needs to mint a preview token and execute its queries. User attributes and SQL filters on the JWT still apply, so row-level access controls are enforced inside the data app exactly as they are on chart tiles.

When this option is off (the default), data app tiles on the dashboard render as a placeholder and no queries run. Turn it on when you trust the embed audience to see the data the app can request and you want the tile to behave the same as it does in Lightdash.

## Write actions

Write actions let embedded users save changes back to Lightdash. When the JWT includes a `writeActions` claim, Lightdash uses a configured actor (a service account or a regular user) to perform the write on behalf of the embedded viewer, and keeps created or edited content inside the spaces the token names.

With `writeActions`, embedded users can:

- Save a new chart from the embedded Explore view.
- Edit an existing embedded dashboard with the React SDK — rename it, add one or more saved charts, and move or resize tiles. See [`Lightdash.Dashboard` edit mode](/embed/react-sdk#with-edit-mode).
- Create a brand-new dashboard with the React SDK using [`Lightdash.DashboardBuilder`](/embed/react-sdk#lightdashdashboardbuilder).

This is useful when you want to let your customers explore data, change charts and dashboards, and save the result back to Lightdash — without giving them a Lightdash login.

```typescript
writeActions?: {
  writeSpaceUuids: string[],          // Required: spaces users can write to; the first is the default
  sourceSpaceUuids?: string[],        // Dashboard and AI agent tokens only: see Add charts from other spaces below
  serviceAccountUserUuid?: string,    // Use a service account as the actor
  userUuid?: string,                  // Or use an existing Lightdash user as the actor
  permissionsMode?: 'default' | 'roles', // Dashboard and AI agent permission mode
  spaceUuid?: string,                 // Deprecated: a single write space; use writeSpaceUuids
}
```

**Rules:**

- `writeSpaceUuids` takes 1 to 100 space UUIDs with no duplicates. Every space must belong to the embed's project. If any one of them doesn't exist or belongs to another project, the token gets no write actions at all. A write space the actor can't create charts in is left out of the save options.
- The first write space is the default: new content is saved there unless the user picks another write space. In AI agent embeds, it also scopes threads.
- `spaceUuid` is still accepted and behaves like a one-entry `writeSpaceUuids`. A token that sets both is rejected.
- You must provide exactly one of `serviceAccountUserUuid` or `userUuid`.
- The actor must belong to the same organization as the project and (for `userUuid`) be active.
- The actor's permissions and space access still apply — the embed inherits whatever the actor can do in each write space.
- When editing or building a dashboard, the add-chart picker lists saved charts from the write spaces and any [source spaces](#add-charts-from-other-spaces).
- Dashboards and charts created or edited through write actions are normal Lightdash objects — they can be viewed and edited from Lightdash and vice versa.
- Newly saved charts are **not** added to the embed allowlist automatically. They behave like normal private content and won't be re-embeddable unless you add them explicitly.
- In AI agent embeds, the name shown next to messages in the chat is the actor's name: the Lightdash user's full name for `userUuid`, or the service account's description for `serviceAccountUserUuid`. Every embedded viewer sees the same name; the `user` claim does not change it. To show a neutral name, such as your product's assistant name, use a dedicated actor: a service account whose description is that name, or a Lightdash user created for the embed.
- API access tokens do not support write actions. They are for supported API reads, such as listing content through the React SDK.

### Configure write actions

Configure write actions from **Settings → Embedding** by toggling **Enable write actions** and selecting:

- **Service account** — the Lightdash actor that performs the write. You can pick an existing service account or create one inline. Only service accounts with a writable role (Admin, Developer, Editor, or an equivalent custom role) can be used.
- **Default space for created content** — the first write space. You can pick an existing space or create one inline. On the Dashboards and Charts tabs, it's the selected dashboard's or chart's space.
- **Additional write spaces** — optional. Embedded users can also edit content in these spaces and choose them when saving. The service account needs edit access to each one.
- **Spaces to add charts from** — optional, Dashboards tab only. Sets [`sourceSpaceUuids`](#add-charts-from-other-spaces).

The settings panel generates a JWT snippet that includes the `writeActions` claim with the selected service account user UUID and the space UUIDs. Copy that snippet into your backend token-generation code.

### Using a service account

Service accounts are the recommended actor for embed write actions because their attribution stays consistent regardless of which embedded user is viewing.

```javascript
import jwt from 'jsonwebtoken';

const token = jwt.sign({
  content: {
    type: 'dashboard',
    dashboardUuid: 'your-dashboard-uuid',
    canExplore: true,                  // Enables Explore in the default permission mode
  },
  writeActions: {
    serviceAccountUserUuid: 'service-account-user-uuid',
    writeSpaceUuids: ['destination-space-uuid'],
  },
  userAttributes: {
    tenant_id: 'tenant-abc',
  },
}, LIGHTDASH_EMBED_SECRET, { expiresIn: '1h' });
```

### Using a regular user

If you want saved charts attributed to a specific Lightdash user (e.g. an internal owner), use `userUuid` instead. The user must be active in the organization.

```javascript
const token = jwt.sign({
  content: {
    type: 'dashboard',
    dashboardUuid: 'your-dashboard-uuid',
    canExplore: true,
  },
  writeActions: {
    userUuid: 'lightdash-user-uuid',
    writeSpaceUuids: ['destination-space-uuid'],
  },
}, LIGHTDASH_EMBED_SECRET, { expiresIn: '1h' });
```

### Save to more than one space

List several spaces in `writeSpaceUuids` to let embedded users write to all of them, for example a personal space and a shared team space:

```javascript
writeActions: {
  serviceAccountUserUuid: 'service-account-user-uuid',
  writeSpaceUuids: ['personal-space-uuid', 'team-space-uuid'],
}
```

When the actor can create charts in more than one of the write spaces, the save dialog shows a required **Space** select that defaults to the first one. Embedded users can only choose among those spaces. `Lightdash.DashboardBuilder` always creates its dashboard in the first write space.

### Add charts from other spaces

Set `sourceSpaceUuids` on a dashboard token to let embedded users add existing charts from spaces they can't write to, such as a shared library of curated charts. It takes up to 100 space UUIDs.

```javascript
writeActions: {
  serviceAccountUserUuid: 'service-account-user-uuid',
  writeSpaceUuids: ['customer-space-uuid'],
  sourceSpaceUuids: ['curated-charts-space-uuid'],
}
```

- The add-chart picker lists saved charts from the write spaces and the source spaces. The actor needs view access to each source space.
- Charts from a source space stay in that space and can't be edited from the dashboard. Charts saved inside a dashboard can't be added from a source space, and SQL charts from a source space can appear in the picker but fail when the dashboard is saved.
- When the claim is set, the token can only list content in the write and source spaces.
- AI agent tokens also accept `sourceSpaceUuids`, but "write" means something different there: the claim expands what the agent can read and search, and which dashboards or charts a thread can bind to, without letting it create or update content in those spaces. See [Access control](/embed/embed-ai-agents#access-control) for AI agent tokens. Chart, metrics catalog, data app, and API access tokens ignore the claim.

## Permission modes

Use `writeActions.permissionsMode` to choose how dashboard capabilities and AI agent access are authorized. Set it in the JWT you sign on your server, not in `content` or an SDK prop. The accepted values are `'default'` and `'roles'`; omitting it is equivalent to `'default'`.

| Embed type | Omitted or `'default'` | `'roles'` |
| --- | --- | --- |
| Dashboard | JWT interactivity flags and their defaults | Only the actor's corresponding embed scopes |
| AI agent | Actor must satisfy AI access prerequisites | Same prerequisites **AND** the actor's `view:EmbedAiAgent` scope |

The mode only switches dashboard capabilities and AI access. Chart, metrics catalog, and AI agent tokens that include `writeActions` also pick up the actor's embed scopes in either mode: for example, the actor's `view:EmbedExplore` enables Explore even when the token omits `canExplore`. The [AI Debug scope](#debug-information) is the exception and only applies in `'roles'` mode. Data app embeds don't use embed scopes.

### Choose the actor and its role

Role checks use the Lightdash user identified by `writeActions.userUuid`, or the service account identified by `writeActions.serviceAccountUserUuid`. Include `writeActions.writeSpaceUuids` and meet the [write-action requirements](#write-actions), even when you are configuring read-only capabilities such as export. Dashboard `'roles'` mode rejects requests if the actor cannot be resolved; it does not fall back to JWT-only permissions.

Configure embed scopes in the **Embedding** section of a [custom role](/workspace-admin/custom-roles), then assign that role to the actor. Built-in roles also provide embed scopes; duplicate a system role if you want a starting point you can edit. The external viewer's `user.externalId` is not the role-bearing actor.

Permissions from the actor's organization and project roles are additive. Removing a scope from one role does not revoke a grant from another role. When testing a restrictive custom role, make sure the actor has no other role that still grants the capability.

### Dashboard capabilities

Both modes require a resolved actor (`serviceAccountUserUuid` or `userUuid`) who can view the dashboard and its project.

**`'default'` (or omitted):** Capabilities come from the JWT's `content` flags (`canExportCsv`, `canExplore`, `canViewUnderlyingData`, etc.), each defaulting to off. This is the existing JWT-only behavior.

**`'roles'`:** Capabilities come entirely from the actor's embed scopes; `content` flags are ignored. Grant each capability as a scope in a [custom role](/workspace-admin/custom-roles) assigned to the actor:

| Scope | Enables |
| --- | --- |
| `view:EmbedExplore` | "Explore from here" |
| `view:EmbedCsvExport` | CSV export |
| `view:EmbedImageExport` | Image export |
| `view:EmbedPagePdfExport` | PDF export |
| `view:EmbedUnderlyingDataView` | View underlying data |
| `view:EmbedDashboardCsvExport` | Export all dashboard tiles |
| `view:EmbedDataApps` | Data app tiles |

Filter interactivity (`dashboardFiltersInteractivity`) and parameter interactivity (`parameterInteractivity`) are unaffected by the mode — they're always controlled by the JWT.

```javascript
// 'roles' mode: capabilities come from the actor's role, not the content flags below
const token = jwt.sign({
  content: {
    type: 'dashboard',
    dashboardUuid: 'your-dashboard-uuid',
    canExplore: true,            // Ignored in 'roles' mode
    canExportCsv: true,          // Ignored in 'roles' mode
  },
  writeActions: {
    serviceAccountUserUuid: 'service-account-user-uuid',
    writeSpaceUuids: ['destination-space-uuid'],
    permissionsMode: 'roles',    // Capabilities now come from the actor's embed scopes
  },
}, SECRET, { expiresIn: '1h' });
```

### AI agent access

Both modes require an AI agent token, a resolved actor who can view the project and create charts in at least one write space, and the existing agent, space, and thread access checks. `'default'` does not mean unrestricted AI access.

To make the actor's role control access to embedded AI, add the mode to the [AI agent token](#ai-agent-token):

```javascript
const token = jwt.sign({
  content: {
    type: 'aiAgent',
    agentUuid: 'your-agent-uuid',
  },
  writeActions: {
    serviceAccountUserUuid: 'service-account-user-uuid',
    writeSpaceUuids: ['destination-space-uuid'],
    permissionsMode: 'roles',
  },
}, SECRET, { expiresIn: '1h' });
```

With `permissionsMode: 'roles'`, the actor additionally needs `view:EmbedAiAgent` to use the agent at all.

## Debug information

Show the AI Debug panel on agent answers so embedded users can inspect prompts, tool calls, and model output.

```typescript
content: {
  type: 'aiAgent',
  canViewDebugInfo?: boolean,  // Shows the Debug panel in 'default' mode
}
```

`content.canViewDebugInfo` only takes effect in `'default'` [permission mode](#permission-modes). In `'roles'` mode, the Debug panel needs the actor's `view:EmbedAiAgentDebug` scope instead; `canViewDebugInfo` is ignored.

## SQL and downloads on answers

**View SQL** and **Download** on an agent's chart or table answers follow the actor's role, independent of `permissionsMode`:

| Control | Requires |
| --- | --- |
| **View SQL** | Actor's `view:Sql` permission |
| **Download** (CSV/image) | Actor's export permissions, same as dashboard export |

There's no JWT flag for these — grant the actor's underlying role the permission if you want embedded viewers to see it.

## User metadata

Identify embedded viewers for query result caching, usage tracking, and (for some embed types) warehouse query tags.

```typescript
user?: {
  externalId?: string,
  email?: string,
}
```

- `externalId` — a stable identifier for the embedded viewer in your system. Lightdash uses it to key query result caching and usage analytics, keeping each viewer's cached results and audit trail separate.
- `email` — shown as a convenience label in Lightdash's project usage analytics alongside `externalId`.

For dashboard, chart, and metrics catalog embeds, `externalId` is also sent as a warehouse query tag on the queries that viewer runs, alongside standard Lightdash tags (user, project, and query identifiers) — use it to attribute warehouse spend or set up per-viewer query tagging in your warehouse. AI agent queries run as the write actor and are tagged with the actor's identity instead; neither `externalId` nor `email` is sent as a query tag for AI agent embeds.

Neither field grants access by itself — the content, write space, and user attribute rules still apply. Both are optional; omit them if you don't need per-viewer tracking.
