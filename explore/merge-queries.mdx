A merge query puts two or more explores side by side in one result. You pick the fields you want from each explore, say which field lines them up, and run. The merged result behaves like any other chart: you can configure it, save it, add it to dashboards, schedule it, and filter it from a dashboard.

Use it when a question spans two explores that share a field at the same grain, such as review sentiment next to return rates for the same product, or orders next to payments for the same month.

## Before you start

Each source of a merge is a normal explore query with its own metrics, dimensions and filters. All explores must be in the same project, and the same explore can be used more than once. You need:

- **A shared field.** A dimension that exists in every source with matching values, such as a product code or a month. This becomes the join key. A merge can join on more than one field.
- **Matching grain.** Every dimension you select from a source must be one of the join keys. This keeps each source to one row per key, so the join never multiplies rows. See [how the join stays honest](#how-the-join-stays-honest).

Anyone who can run queries in the explore can merge. There is nothing to install and no change to your dbt project.

## Which join type to choose

The three options answer one question: when a key exists in only some sources, what happens to it?

| Option | SQL equivalent | Keeps | Use when |
| --- | --- | --- | --- |
| **Matches only** | Inner join | Only keys found in every source. Anything unmatched is dropped. | A row missing any measure would be misleading. |
| **From** _first explore_ | Left join | Every key from the first explore. Other sources' columns are blank where they have no match. | The first explore is the list you report on. |
| **All rows** | Full outer join | Every key from any source. Blanks wherever a source has nothing. | You want to spot keys that exist in some sources only. |

## How the join stays honest

A merge is only safe when each source has exactly one row per join key. Because an explore query groups by its dimensions, that comes down to one rule: **every dimension you select in a source must be a join key.** Metrics are already one value per key, so any number of them is fine.

When a selection breaks the rule, the query refuses with a message rather than multiplying rows. Either add that dimension as another join condition in every source, or remove it.

For example, reviews by `product` merged with returns by `product`, joined on product, works. Reviews by `product` and `month` merged with returns by `product`, joined on product only, refuses, because the review side has many rows per product. Add `month` to both sides and to the join conditions and it works again.

### Repeat values

Sometimes the extra rows are what you want, such as a product's return rate shown on every month of its reviews. The refusal message offers to repeat the other sources' values on every row of the finer-grained source. Their values then appear once per matching row, and their columns have no totals, because a sum would count each value once per repeat. Only one source can keep dimensions that are not join keys. Choose **Stop repeating** to go back.

## Filters

Filters on a source apply to that source before the join. A [dashboard filter](/explore/dashboards/filter) on a merged chart is pushed into every source that has the field, so a date filter narrows every explore rather than only the merged output. A dashboard filter on a column that exists only in the merged result, such as a merge table calculation, is refused, because merges have no filter step after the join.

## Current limits

| Area | Today |
| --- | --- |
| Join key formatting | The merged key column shows its underlying value. A month key shows as a full date rather than a month label. |
| Row limits | Each source runs with its own row limit. If a source is cut off by its limit, the merge refuses instead of returning a partial answer. Narrow that source with a filter or raise its limit. |
| Dashboards | Date zoom and dashboard sort overrides are not applied to merged chart tiles. |
| Sources | Explores from the same project. |
