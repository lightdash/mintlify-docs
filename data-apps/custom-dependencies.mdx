<Info>
  Custom dependencies are off by default. An organization admin turns them on under **Settings → Data apps → General** with **Allow custom dependencies**. Uploading an app that declares custom dependencies also requires the `manage:DataAppDependency` permission, granted only to admins by default.
</Info>

By default, apps build against a fixed, pre-installed library set that Lightdash vets and ships — edits to `package.json` are ignored. Turning custom dependencies on lets an app pull additional packages from the public npm registry into the build sandbox, which is why it's opt-in:

* A third-party library becomes part of your app. It can shape how the app behaves and touch any data the app is allowed to query, so the main consideration is trust in the libraries you choose. That's also why the upload permission (`manage:DataAppDependency`) is restricted to admins by default.
* Lightdash adds several layers of protection to reduce that risk: every uploaded version is screened against the OSV malicious-package feed, installs use `--frozen-lockfile --ignore-scripts` so lifecycle scripts can't run, the sandbox has no access to Lightdash credentials, and network egress is limited to the npm registry.

With custom dependencies enabled, you can extend the pre-installed set from the app folder. Follow [Local data app development](/workflow/local-data-app-development) to download or create the app first:

```bash
cd lightdash/apps/revenue-explorer
pnpm add deck.gl          # updates package.json AND pnpm-lock.yaml
lightdash upload --apps revenue-explorer
```

Both files matter: the dependency set is `package.json` plus a matching `pnpm-lock.yaml` (the server installs with pnpm, so an npm lockfile won't do). On upload, the CLI shows what you're adding and asks for confirmation:

```text
"revenue-explorer" declares custom dependencies that will be installed in the build sandbox:
  + deck.gl@^9.3.5 (not in default template)
Upload "revenue-explorer" with custom dependencies?
```

If the upload fails with `Custom app dependencies are not enabled for your organization`, you have the `manage:DataAppDependency` permission, but custom dependencies aren't turned on for your organization. Ask an organization admin to turn on **Allow custom dependencies**. Turning it off blocks new uploads with custom dependencies; apps that already use them keep building.

**Rules the CLI and server enforce:**

- Registry semver specs only (`^9.3.5`, `~1.2.0`, ranges). No `git:`/`file:`/URL specs and no dist-tags like `latest`.
- At most 60 direct dependencies; lockfile ≤ 2 MB and consistent with `package.json`.
- Every version is screened against the OSV malicious-package feed at upload; known-bad versions are rejected outright.

**Additional hardening:** install scripts also never run on your machine — the scaffolded `.npmrc` sets `ignore-scripts=true`; keep it. Self-hosted instances can further tighten the policy by requiring a minimum package release age (`LIGHTDASH_APP_DEPENDENCY_MIN_RELEASE_AGE_DAYS`) or pointing installs at an internal mirror (`LIGHTDASH_APP_DEPENDENCY_REGISTRY_HOSTS`).

<Note>
  Apps can't install private packages. There's no setting for a private registry or a registry auth token, such as a GitHub Packages token, so every dependency must be public on npm. `LIGHTDASH_APP_DEPENDENCY_REGISTRY_HOSTS` changes which registry hosts the sandbox can reach, but it can't add authentication. To keep branding private, use [themes](/data-apps/customize-themes), whose assets stay in your organization.
</Note>

**Uploads are the only way to change dependencies.** When someone iterates on the app in the UI, the AI builder can edit `src/` but the stored dependency set is restored as-is — its `package.json` edits are ignored. Dependency changes on a version are visible in the version history.
